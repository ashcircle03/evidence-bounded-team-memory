# 팀 메모리 Retrieval 평가셋 v1

PR #3의 F02(새 기록을 비교할 과거 구절 선택)와 F05(질문에 필요한 근거 선택)를 평가하기 위한 로컬 고정판이다. 403개 호출의 입력과 정답을 별도 파일에 저장했다. 데이터셋 생성 및 무결성 검사를 완료했다. 검색기 실행 결과는 후속 평가에서 기록한다.

| 출처와 과제 | 개발 | 평가 | 별도 진단 | 후보 풀 |
| --- | ---: | ---: | ---: | --- |
| 한국어 합성 팀 기록 F02 | 50 | 50 | | 시나리오 100개에서 등록 시점의 과거 기록만 노출 |
| 같은 시나리오의 F05 | 50 | 50 | | 후속 기록이 추가된 시점의 원문과 검토 상태 |
| SQuAD 2.0 영어 F05 | 100 | 100 | | 기사 20편의 단락 612개. 질문마다 해당 기사 전체 단락에서 검색 |
| 기존 Aimers 한국어 F05 | | | 3 | 6개 발췌문을 공유하며 문항마다 두 발췌문 필요 |
| 합계 | 200 | 200 | 3 | 고유 원문 문자열 2,138개 |

## 실제 실행 입력

1. [cases.jsonl](v1/cases.jsonl)에서 case를 읽고 corpus ID로 [corpora.jsonl](v1/corpora.jsonl)의 독립된 workspace를 선택한다. 행 순서는 검색 점수나 최신성으로 사용하지 않는다.
2. F02는 history ID에 해당하는 문서만 색인하고 incoming 문서를 비교 요청으로 보낸다. F05는 해당 corpus 전체를 색인한 뒤 query 문자열을 전달한다. 조건은 직접 제공하지 않는다. reviews가 있으면 해당 snapshot에 미리 존재하는 관계·판정 상태로 취급한다. 원문과 관계를 제품 포트에 적재하는 어댑터는 후속 실행 작업이다.
3. 검색 결과에는 case ID, 순위, source ID, start, end를 남기고 F05는 전달한 검토 상태 ID도 기록한다. [gold.jsonl](v1/gold.jsonl)은 채점기만 읽는다. source ID를 내부 ID로 변환하는 도구는 양방향 대응표를 유지한다.
4. 각 required 내부 목록은 허용 가능한 대안이다. 그중 하나의 source ID가 일치하고 검색 구절이 정답의 Unicode [start,end) 범위를 모두 포함하면 해당 그룹을 회수한 것이다. 바깥 목록의 그룹은 모두 필요하다. required_review_ids가 있으면 해당 상태 근거도 최종 bundle에 있어야 한다. category는 결과 분석용이다.

## 평가 방법

- F02 양성 80건에서 후보 source recall@1/3/5와 span recall@1/3/5를 별도로 계산한다. 전자는 올바른 과거 문서를, 후자는 문서 안에서 실제 주장을 회수했는지 측정한다. 음성 20건은 빈 이력 10건과 비관련 이력 10건으로 나눠 잘못 후보를 반환한 비율을 보고한다. 양성은 비교 후보가 16개다.
- F05는 근거가 있는 문항에서 정답 구절 회수율과 모든 필수 구절을 찾은 문항 비율을 함께 보고한다. 검토 상태가 필요한 문항은 원문 양쪽과 상태를 모두 전달한 비율도 기록한다. 합성 근거 없음 10건은 별도로 no_hits 비율을 집계한다. 실패 응답은 no_hits로 세지 않는다.
- 근거 길이와 K를 동일하게 고정하고 결과에 명시한다. 큰 구절 하나가 정답을 덮는 효과를 보려면 반환한 총 문자 수도 함께 보고한다. 한국어 합성·영어 공개·Aimers 점수는 따로 집계한다. 개발 분할에서 K·임계값을 선택한 뒤 평가 분할을 사용한다.

## 구성과 해석

**한국어 합성.** 정정, 상충 보고, 재검토, 조건 추가, 첫 등록을 각각 20개 시나리오로 구성했다. 승인자·회귀 시험 횟수·보관 기간·검수 장소·배포 요일을 바꾸고, v1/v10 같은 인접 조건, 같은 팀의 다른 업무, 협력사의 비슷한 기록을 넣었다. F02 정답은 새 기록이 직접 지칭하는 선행 주장이다. F05는 인접 조건 20건, 정정·상충·재검토·조건 추가 각 15건, 첫 등록 조회 10건, 근거 없음 10건이다. 검토 상태는 Retrieval 단독 진단용 입력이다. Relations의 자동 판정 성능은 이 데이터로 측정하지 않는다. 같은 시나리오의 두 호출은 같은 분할에 둔다. 개발·평가 프로젝트명은 분리했으나 문장 템플릿을 공유하므로 독립적인 실제 팀 기록 일반화 성능으로 해석할 수 없다.

**공개 자료.** Stanford Question Answering Dataset 2.0 공식 개발 파일에서 답이 있는 질문만 사용했다. 기사 단위로 분할하고 기사마다 서로 다른 10개 단락에서 질문을 한 개씩 선택했다. 원래의 질문 ID와 사람 주석의 답 구간을 보존했다. 이 벤치마크는 기사 내 근거 위치 찾기로 변환한 공개 개발 자료다. 원래 주석이 모든 대안 근거 단락을 망라하지 않으며, 전체 문서 검색·한국어 버전 조건·검토 상태를 평가하지 않는다. SQuAD 파생 데이터는 CC BY-SA 4.0을 따른다. 변환 내용은 질문·기사 부분 선택, 단락별 검색 후보 구성, 원본 주석의 구간 형식 변환이다. [Stanford 원본과 저자 정보](https://rajpurkar.github.io/SQuAD-explorer/) · [라이선스](https://creativecommons.org/licenses/by-sa/4.0/)

**Aimers.** 기존 팀 질문 t01–t03을 한 번씩 사용했다. 실행 124526의 direct 입력에서 원 질문과 공급된 인용문을 가져왔고 모델 답변은 사용하지 않았다. [보존한 문항과 발췌문](aimers.json) · [기존 평가 기록](../../results/answering-port/team-question-pairs/ratings.json). 전체 보고서의 검색 성능과 별도로, 작은 후보 풀에서 양쪽 근거가 모두 전달되는지 확인한다.

## 검증과 재생성

이 디렉터리에서 Python 3.9 이상으로 실행한다. 고정판 검증에는 인터넷과 모델이 필요 없다.

```sh
python3 validate.py
shasum -a 256 -c SHA256SUMS
```

재생성할 때는 [공식 dev-v2.0.json](https://rajpurkar.github.io/SQuAD-explorer/dataset/dev-v2.0.json)을 내려받아 다음과 같이 실행한다. 빌더는 원본 SHA-256을 대조한다.

```sh
python3 build.py /path/to/dev-v2.0.json --output /tmp/retrieval-v1-rebuild
diff -qr v1 /tmp/retrieval-v1-rebuild
```

검증기는 분할별 수량, ID 연결, 개발·평가 간 동일 원문·질문 중복, 원문 인용 구간, F02 후보의 시점 가시성, F05 상태 참조를 검사한다. 합성 시나리오의 자연스러움과 실제 검색 난이도는 이 구조 검사와 별도로 평가해야 한다.
