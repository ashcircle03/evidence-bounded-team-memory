Starting point: commit `60aad09`. Local CPU development may use the published CPython 649/749, 703/779 and 690/810 development cases, Aimers, EverMem topic 01 and unit fixtures. Freeze production code and prompts before constructing the final casebook. Keep every original, distraction and contradiction from one incident together. Do not tune on final cases, even on a miss. Record incomplete rows and infrastructure failures. A repair to collection or replay must preserve the frozen inputs and separately document any change.

Existing Aurora ceiling is 69 single-GPU minutes and 40 CPU-only minutes. At registration the local dispatch records 3,858 and 2,387 elapsed seconds respectively, including failed runs. This pilot may request one GPU for up to four minutes (8 CPUs, 48 GB, no requeue). No new CPU allocation. Freeze inputs locally, run both arms on the same compute node with the existing Qwen2.5-3B-Instruct revision, BF16, greedy decoding and the same per-task source and generation ceilings. Record actual calls, tokens, returned strings and evidence. No automatic budget increase or second holdout attempt.

## Cases and metrics

- **Ordinary QA:** 10 or more distinct, previously unused engineering decisions or project records. Use independently inspectable, dated public Git objects for original questions. Include several answer types. Each clean case has an answer and one or more permissible source spans fixed by a human-readable key. Repeat its exact question with an unrelated disagreement added. Count an answer only when it conveys the requested fact and cites its visible, genuine supporting source. Target at least 80% and zero paired losses among originally correct answers. Separately replay the two previously correct EverMem topic 01 development queries through the candidate. Do not count them as holdout successes.
- **Conflict QA:** 10 or more distinct incidents. Introduce a clearly disclaimed, authored counter-report for a precise fact in the same scope as a held-out original. Preserve the original, vary the author and wording, and include distractors. Never present counterfactuals as claims by a real upstream author. Require both incompatible answers with their respective source locations and actual supporting excerpts. Target at least 80%. Report these as controlled conflicts, not naturally occurring upstream disputes.
- **Review:** 10 or more positive and 10 or more negative incoming records from distinct held-out events, with multiple searchable historical records per incoming update. Use project work across multiple domains, conditions, and action types. Mark reconstructions or simulated messages. Include lexical near-misses, same-scope confirmations and hypotheses among negatives. No question, candidate target, answer key, or correct action in the review input. Supply only the common project goal, prior records and incoming source. Require correct prior source, grounded reason for reopening, the material new condition/evidence, and a suitable follow-up. Count an unsolicited actionable proposal on a negative as a false positive. Targets: at least 80% positives, no more than 10% false positives.
- Record each arm's outcome, cited excerpts and raw call. A broad excerpt or copied document that happens to contain a keyword does not suffice. Review outputs for semantic correctness and identify any interpretation requiring adjudication. Report positives and negatives separately, paired gains and losses, and the denominator. For adoption, require the review thresholds, two additional correct decisions on *distinct* events, and no loss of a previously correct baseline decision. Report QA and review adoption separately. Label sole-author annotations and small-sample results as such.

## Arms and freeze

Use ordinary source retrieval plus the same Qwen as the simple arm. The candidate may change how evidence is broken up, ranked and aligned. Compare from the same available corpus, access time, input ceiling and decoding budget. No label-derived source shortlist or oracle passage. Selection of a pre-cited passage is not automatically an answer. Separate the prior historical benchmark scores from this direct comparison.

The deliverable includes a two-checkout Git workflow, tentative and approved state, raw outputs, scoring/replay commands, a report and a public checkout. If targets fail, publish measured results and retain the strongest verified default. Reserve fresh cases for further changes.
