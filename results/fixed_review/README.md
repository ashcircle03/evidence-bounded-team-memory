# 올바른 두 문단에서 출발하는 재검토 판정

**수정안을 기본 전략으로 채택하지 않았다.** 올바른 과거·신규 문단을 지정하면 새 Git 회귀 6건에서 조건까지 맞게 전달한 제안이 0건에서 3건으로 늘었다. 그러나 원문에서 문단을 직접 고르게 하면 두 방식 모두 0/6이었다. 실제 독립 변경에 대한 오탐은 0/6에서 5/6으로 늘었다.

## 같은 근거에서 보류한 이유

최초 `checkout -b`에서는 작업 트리를 실제로 채워야 한다. 과거 기록은 새 브랜치를 만들 때 트리·인덱스 갱신을 생략하기로 했고, 후속 보고는 최초 checkout에 이 최적화를 적용한 회귀와 별개로 파일시스템 검사를 뒤로 미루는 비용 최적화도 설명했다. [과거 결정](https://github.com/git/git/commit/fa655d8411cc2d7ffcf898e53a1493c737d7de68) · [후속 보고](https://github.com/git/git/commit/8424bfd45b291a56594f0289dc6af22e900a1d88)

이전 방식은 문서와 문단의 두 점수가 모두 양수여야 제안한다. 같은 과거 문단과 신규 문단을 고정했을 때, 과거를 먼저 보이는 조건과 새 보고를 먼저 보이는 조건의 문단 점수는 **둘 다 +2.50**이었다. 문서 전체의 점수만 **+0.75에서 −8.25**로 바뀌었다. checkout에서는 문서 판정의 부호가 뒤집힌 것이 보류의 직접 원인이다. send-email 역시 문단 점수는 모두 양수였지만 문서 점수는 +2.75에서 −11.75로 뒤집혔다. 반면 빈 트리 사례에서는 문단 점수도 +2.0에서 −5.0으로 바뀌었다. 한 사례의 원인으로 전체를 설명할 수 없다. [동일 문단·양측 점수](gate-diagnosis.json)

수정안은 동일한 두 문단으로 두 가지 질문을 평가한다. 새 보고가 그 과거 결정의 예외를 보이는지와, 기존 결정의 조건을 건드리지 않는 독립 변경으로 설명할 수 있는지를 묻는다. 두 질문의 점수 차이를 두 표시 순서에서 구한 뒤 평균낸다. 설명은 원래 시간 순서로 배치하고, 새 보고에서 조건을 뒷받침할 문장 한 개를 모델이 먼저 선택한다. 후보를 찾는 부분에는 이전 선택기를 그대로 사용했다. 두 순서를 계산에 포함하므로 최종 행동이 순서에 따라 바뀌지 않는 것은 설계의 성질이다. 개별 판정은 여전히 민감했다. 예를 들어 git am의 올바른 근거 쌍은 대비 점수가 −10.25, +13.625였다. [전략 구현](../../team_memory/fixed_review.py) · [실제 점수](stage-scores.json)

## 설명에서 바뀐 조건을 놓친 이유

checkout에서 기존 설명기는 판정을 강제로 통과시켜도 최초 checkout 예외 대신 비용이나 파일시스템 접근을 적용 조건으로 썼다. 수정안의 문장 선택기는 최초 checkout을 설명한 문장에 −7.25, 비용 문장에 −18.625, “이 회귀는 해당 커밋에서 생겼다”는 참조 문장에 −6.25를 줬다. 가장 높은 참조 문장을 강조한 뒤 작성한 제안은 최초 checkout을 누락하고 회귀를 도입한 커밋이 회귀를 고쳤다고 뒤집었다. 두 원문을 찾아도 **화제가 일치하는 문장과 실제 적용 조건을 설명하는 문장**을 구분하지 못한 것이다.

기존 설명기의 추가 대조에서는 같은 GPU에서 한 번에 한 입력만 생성했다. 비용 문장만 지워도 최초 checkout 예외를 “모든 checkout”으로 넓혔고, 예외 문장만 지우면 원문에 없는 성능 회귀를 제시했다. 비용 문장을 앞으로 옮기는 것만으로도 예외를 정확히 복구하지 못했다. 여기서 확인한 것은 입력 편집에 따른 출력 변화이며 모델 내부의 원인을 단정할 수는 없다. [문장 삭제·이동에 따른 원출력](explanation-singletons.json)

수정안에서 두 문단과 설명 지시는 한 글자도 바꾸지 않고 강조 문장만 교체했다. 실제로 선택된 커밋 참조 문장을 주면 같은 오답이 재현됐다. 사람이 최초 checkout 문장을 지정하면 초기 브랜치에서 갱신을 생략한 판단을 다시 볼 필요가 있다고 썼지만, 원문에 없는 파일시스템 접근 문제를 이유로 덧붙였다. 비용 문장을 지정하면 비용 쪽의 오답으로 돌아갔다. 강조를 비우면 초기 브랜치 생성에서 전체 checkout 생략을 돌아봐야 한다고 썼다. 즉 강조 문장 선택과 그 문장에서 설명을 만드는 단계 모두에서 오류가 관측됐다. 이 사후 대조는 신규 사례 적중 수에 포함하지 않았다. [강조 문장만 바꾼 네 원출력](focus-control.json)

## 처음 평가한 실제 Git 사례

Git 회귀 6건과 각각 같은 영역에서 별개의 동작을 수정한 실제 보고 6건을 사용했다. 과거 원문 전체에서 시작하는 평가와 올바른 두 문단을 공급하는 진단은 분리했다. 재검토를 요청한 경우에도 양측 인용과 변경 조건 설명을 모두 맞혀야 적중이다. [사전 평가 기준](../../evaluation/fixed_review/PROTOCOL.md) · [사건별 제안·원문·채점](cases.ko.md)

| 조건 | 판정기 | 회귀에 제안 | 변경 조건까지 맞힌 제안 | 독립 변경에 오탐 |
|---|---|---:|---:|---:|
| 문단 고정, 과거 먼저 | 이전 pairwise | 0/6 | 0/6 | 0/6 |
| 문단 고정, 새 보고 먼저 | 이전 pairwise | 0/6 | 0/6 | 0/6 |
| 문단 고정, 양 순서 결합 | 수정안 | 6/6 | 3/6 | 3/6 |
| 원문 전체, 실제 제안 | 이전 pairwise | 1/6 | 0/6 | 0/6 |
| 원문 전체, 실제 제안 | 수정안 | 6/6 | 0/6 | 5/6 |

- **판정과 설명의 효과를 분리하면** 올바른 문단을 주고 보류 여부와 관계없이 설명을 쓰게 했을 때, 과거 먼저의 기존 설명기는 CVS·SVN·심볼릭 링크 3/6, 새 보고 먼저는 0/6, 수정안은 CVS·하위 테스트 출력 경로·심볼릭 링크 3/6이었다. 기존 과거 먼저 조건과 비교하면 설명 자체의 적중 수는 늘지 않았다.
- **같은 새 보고에 다른 과거 결정을 붙이면** 수정안은 무관한 조합에도 5/6번 제안했다. 예컨대 CamelCase 별칭 회귀는 실제 과거 결정에서 +6.19, 무관한 과거 결정에서 +6.25였다. 올바른 git am 근거 쌍(+1.69)보다 독립적인 clone 심볼릭 링크 수정(+8.25)이 높아, 이 사례들에서 단일 문턱을 올려 양성을 전부 살리면서 음성을 모두 막을 수 없다. 새 보고가 실제 버그를 설명한다는 사실만으로 특정 과거 결정을 다시 열 근거가 되지는 않는다.
- **원문에서 직접 고른 경우** 수정안은 양성 6건 중 5건에서 과거 문서까지는 찾았지만, 과거·신규 문단을 동시에 맞힌 경우는 0건이었다. 별칭·CVS·하위 테스트에서는 구체적 예외보다 회귀가 어느 커밋에서 생겼는지 적은 문단을 선택했다. SVN은 다른 과거 결정을 골랐다. 심볼릭 링크와 git am은 새 문단이 맞았으나 과거 문단이 채점 기준을 충족하지 않았다.
- **채택 판단**. 동일 원문 쌍에서 순서 뒤집힘은 해소했지만 오탐을 막고 실제 근거 있는 재검토를 늘리는 기준은 충족하지 못했다. 실험은 `pull --strategy fixed-review`로 재현할 수 있다. 다음에는 동일 보고를 그대로 두고 과거 결정만 맞는 것과 틀린 것으로 바꾼 쌍에서, 어떤 구절이 *그 결정*의 예외인지 식별하는 능력을 먼저 평가하는 게 타당하다. 결과를 보고 정한 임곗값으로 이 사건들을 다시 성공 처리하지 않았다. [실제 집계](counts.json)

이 소규모 평가는 한 저장소에서 기존 실험과 겹치지 않는 보고를 골라 구성했다. 알려진 회귀 보고는 원인 커밋을 직접 언급하기도 하고 후보 이력은 두 개다. 원문의 허용 구절과 채점 기준을 추론 전에 고정했으며, 서술 평가는 방식과 순서를 숨긴 카드에 대해 한 평가자가 수행했다. 같은 Qwen2.5-3B-Instruct, BF16, greedy, 재검토 설명 96토큰 한도를 썼다. 수정안은 두 가설과 두 표시 순서를 평가하므로 모델 호출 예산까지 맞춘 성능 비교는 아니다.

## 기존 QA 보존

기존 성공 20문항(일반 16, 다중 근거 4)의 원래 Qwen 입력, 배치 이웃·행 위치·생성 상한, QA 파서를 복원했다. **20/20에서 정답·상태·인용문·출처가 모두 동일**했다. 136개 호출에는 원 배치를 재현하기 위한 이웃이 포함된다. 재검토 수정안은 QA 검색기에 개입하지 않는다. [문항별 답과 근거](qa.ko.md) · [채점 전후 JSON](qa-historical.json)

실제 Git push/pull로 미승인 제안이 생긴 두 사건에서 같은 원문만 가진 대조 복제본과 비교했다. 제안은 별도 검토함에 남았고 QA 프롬프트의 해시는 양쪽에서 같았다. 이 입력을 대조·실험 각각 독립적으로 재생성해 인용 파서까지 통과시켰다. checkout에서는 둘 다 같은 커밋의 같은 구간을 인용해 `checkout.optimizeNewBranch`라고 답했다. 새 CVS 문항은 양쪽 모두 인용 검증에 실패했다. 따라서 이 두 건은 결과 2/2 보존, 실제 정답과 인용 성공은 각 1/2이다.
