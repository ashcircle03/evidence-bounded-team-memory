# 같은 새 보고로 실제 재검토 대상과 비슷한 결정을 구별할 수 있는가

각 사건마다 새 보고는 한 글자도 바꾸지 않고 과거 결정 하나만 교체했다. 첫 이력에는 실제 재검토 대상과 주제만 가까운 결정이 있다. 둘째 이력에는 가까운 결정과 같은 분야의 다른 결정이 있다. 어느 쪽이든 후보가 두 개라서 항상 하나를 고르는 방식도, 항상 보류하는 방식도 양쪽을 맞힐 수 없다. 양성의 적중은 **실제 발행한 제안이 올바른 이전 결정과 새 보고의 근거 구절을 인용하고, 어느 조건에서 어떤 동작이 바뀌었는지를 설명**한 경우다. 대안 원문과 그 결정이 다루는 다른 동작까지 맞혔는지를 더 엄격한 구별 성과로 따로 집계했다.

## 첫 실험 · 출처를 직접 지목하지 않아도 대비가 가능한가

새 Git 보고 6개에서 같은 Qwen2.5-3B-Instruct로 검증했다. 두 결정을 한꺼번에 비교하고 ‘해당 없음’도 고를 수 있게 했다. 선택지가 모든 글자·위치를 한 번씩 차지하게 회전해 평균 점수로 결정한 뒤, 선택한 세 문단만으로도 같은 대상을 지목해야 제안하도록 했다. 계산량을 맞춘 실험은 아니다. [사전 계획](../../evaluation/contrast_review/PROTOCOL.md)

| 실제 Git 원문 | 혼합 이력에서 올바른 대상에 제안 | 허용된 과거·신규 근거 쌍 | 변경 조건까지 맞힌 제안 | 무관한 두 결정에 오탐 |
|---|---:|---:|---:|---:|
| 제품 기본 simple | 5/6 | 2/6 | 별도 설명 없음 | 6/6 |
| 이전 pairwise | 2/6 | 1/6 | 0/6 | 1/6 |
| 직전 fixed-review | 5/6 | 2/6 | 1/6 | 6/6 |
| 새 contrast-review | 0/6 | 0/6 | 0/6 | 0/6 |

실제 대상이 있던 6건 중 5건에서는 문서 비교에서 ‘해당 없음’이 이겼다. difftool은 문서 비교를 통과했지만 선택된 구절끼리 비교하자 같은 대상이 나오지 않았다. 사람이 세 구절을 미리 지정한 보조 실험에서도 변경 조건과 대안 구별까지 맞힌 제안은 1/6(commit slab), 무관한 두 결정에 대한 오탐은 1/6이었다. 구절을 찾는 문제를 제거해도 무엇이 실제로 영향을 받는지 판정하는 문제가 남았다. [사례별 원문·설명](cases.ko.md) · [방식별 집계](counts.json)

SHA와 후보 결정의 인용된 제목 문자열을 가린 보조 조건에서는 contrast-review와 직전 방식의 근거 있는 적중이 각각 0/6, 2/6이었다. 단순 마스킹으로 직접 참조가 전부 제거된다고 가정하지 않았다. 후보 순서를 바꾸어 새 전략을 다시 실행한 원문 혼합 6건과 음성 6건에서 결과가 동일했다. 항상 보류했으므로 이 일치 수 자체는 구별 능력의 증거가 되지 않는다.

## 두 번째 실험 · 명시적인 회귀 귀속과 동작 근거를 따로 검증

첫 6건을 본 뒤 `referenced-review`를 추가하고 **별도의 Git 보고 5건**을 선정했다. 보고에서 회귀를 특정 이전 변경에 귀속하는 표현을 찾고, 그 뒤 ID가 실제로 존재하는 과거 출처 하나에 고유하게 대응하는지 확인한다. 특정할 수 있으면 귀속 표현·변경을 보여주는 구절·과거 결정 및 대안 구절을 원문 위치에 연결해 Qwen에 설명을 요청한다. 언급한 대상이 이력에 없거나 유일하게 특정할 수 없으면 보류한다. 인식 가능한 귀속 표현이 없을 때는 첫 대비 방식으로 돌아간다. 이 구현이 처리하는 직접 참조는 Git 커밋 ID 또는 그 ID가 붙은 URL이다. [후속 평가 기준](../../evaluation/contrast_review/validation/PROTOCOL.md) · [구현](../../team_memory/referenced_review.py)

| 독립된 후속 Git 보고 5건 | 올바른 대상에 제안 | 과거·신규 구절 모두 정확 | 대안의 구절도 정확 | 내용까지 맞힌 재검토 | 무관한 두 결정에 오탐 |
|---|---:|---:|---:|---:|---:|
| 직전 fixed-review | 5/5 | 2/5 | 제공하지 않음 | 0/5 | 5/5 |
| 첫 대비 방식 | 0/5 | 0/5 | 0/5 | 0/5 | 0/5 |
| 귀속 표현까지 확인한 수정안 | 4/5 | 3/5 | **3/5** | **0/5** | **0/5** |

‘대안의 구절도 정확’은 **과거 대상·새 보고·비슷한 대안** 세 구절이 모두 맞은 횟수다. 발행한 네 제안에서 대안의 원문 자체는 4/4 맞았다. 원문 이력에서 무관한 단일 결정만 남겨도 최종 방식의 오탐은 0/5였다. 반면 ID와 인용된 제목을 가리면 올바른 대상이 있어도 0/5 제안했다. 보고의 내용만으로 관계를 찾아냈다고 볼 수 없다. 단순 기본 전략은 원문 양성에 5번 제안해 올바른 대상 4/5, 양측 문단 3/5였고 원문 음성에서는 제안 4번·형식 오류 1번이었다. [후속 사건별 원문과 채점](validation/cases.ko.md) · [전체 집계](validation/counts.json)

| 새 보고 | 최종 방식이 찾은 구별과 남은 오류 |
|---|---|
| [훅 호출 여부](https://github.com/git/git/commit/4369e3a1a39895ab51c2bef2985255ad05957a20) | 훅 호출 여부를 전달하는 변경과 훅을 새 라이브러리로 옮긴 변경을 원문으로 구별했다. 새 보고는 `run_commit_hook()`가 플래그를 `run_hooks_opt()`로 넘기지 않았고 `push_to_checkout()`는 제대로 넘겼다고 한다. 모델은 `push_to_checkout()`가 `run_commit_hook()`에 넘겼다고 두 경로를 잘못 이었다. |
| [객체 헤더 오류](https://github.com/git/git/commit/4627c67fa68d5669be511962a6437a11c0db3c99) | 정확한 과거 결정을 찾았지만 새 보고에서 실패 종류를 구분하는 문단 대신 커밋과 테스트를 소개하는 문단을 인용했다. |
| [빈 reflog](https://github.com/git/git/commit/57be9c6deeb1be7c3ce6270df52473eddc09a86c) | null OID에 non-NULL이 돌아오는 변화와 대안의 `--stale-fix` 원문까지 찾았다. 제안의 설명이 실제 파싱 오류를 잘못된 객체 역참조 가능성으로 바꿨고, 대안 설명에서는 누락 객체 허용을 빠뜨렸다. |
| [셸 프롬프트](https://github.com/git/git/commit/1e4119c81b3e203e1729e03be6e4a53eb9207f5c) | zsh가 기본적으로 PS1을 확장하지 않아 변수명이 그대로 찍히는 문제와, 별개의 upstream 브랜치 표시 변경을 각각 인용했다. 모델은 올바른 증상을 짚은 뒤 근거에 없는 `set -o prompt` 옵션을 해결 조건으로 덧붙였다. |

두 차수의 결과는 합산하지 않았다. 다섯 보고 모두 과거 커밋을 언급해 직접 참조의 효과를 보기 유리하며, 같은 Git 프로젝트의 소표본이다. 단일 평가자가 방식·순서를 숨긴 설명을 읽었고, 핵심 일부가 맞더라도 근거 없는 추가 판단은 엄격 채점에서 오답이다. 원문들이 변경과 대안의 차이를 담고 있는지와 모델이 이를 정확하게 설명했는지를 분리했다. 후속 원문 혼합·음성 10건 모두 후보 순서를 뒤집어 재실행해 같은 결과를 확인했다. [판정 근거](validation/ratings.json)

## QA 보존과 채택 판단

원래 성공했던 일반 16문항·다중 근거 4문항에서 원래의 Qwen 설정, 배치 이웃·행 위치와 채점기를 복원했다. 첫 방식과 최종 수정안 모두 20/20에서 답·상태·인용문·출처가 정확히 같았다. 추가로 최종 방식이 실제로 미승인 제안을 만든 두 Git pull에서, 동일한 원문만 가진 복제본과 별도로 QA를 다시 생성했다. 훅 질문의 답은 두 쪽 모두 `invoked_hook`, 프롬프트 질문은 모두 `zsh`였고 인용 위치와 텍스트까지 일치했다. [기존 QA 문항별 결과](validation/qa.ko.md) · [실제 Git pull과 QA 원출력](validation/comparison.json)

**기본값 채택은 보류했다.** 이번에 개선된 부분은 명시적 참조가 있는 기록에서 무관한 결정을 보호하면서 맞는 구절을 함께 모으는 기능이다. 최종 제안은 조건·인과관계까지 설명해야 하므로 채택 조건을 충족하지 못했다. 다음 검증에서는 같은 세 구절을 고정하고, 원문의 함수·동작·조건에 없는 단어나 뒤바뀐 주어가 제안에 들어가는지 검사할 수 있다.


실험 전략은 `python3 -m team_memory --store shared-records pull --model /path/to/Qwen2.5-3B-Instruct --strategy referenced-review`로 실행할 수 있다. 새 제안에 대상과 새 보고의 원문, 비슷한 결정의 다른 구절, 어느 결정을 지목한 표현인지가 위치와 함께 저장된다. 같은 모델의 집계라도 전략별 추론량은 다르다. Aurora Slurm 119299~119303 다섯 작업의 종료 상태·종료 코드·완료 JSON과 입력 해시를 확인했다. 두 판본의 사전 동결 파일 및 실제 제출 아카이브의 코드도 대조했다. GPU 할당은 이번 목표 6분 6초, 캠페인 누적 107분 57초/120분이었다. 단위 테스트 50개가 통과했다. [작업별 자원·해시](runs.json)
