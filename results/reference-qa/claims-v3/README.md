# 주장별 근거를 먼저 선택하는 QA 후보 평가

**기존 QA에는 `attributed`를 유지한다.** `claims`는 원문의 근거 구절을 먼저 선택하고 그 구절로 주장을 작성했다. 순서만 바꾼 두 입력에서 상충하는 값은 모두 반환했지만, 한쪽 순서에서는 인용에 어떤 설정의 값인지 빠졌다. 기존 20문항에서도 답 내용은 15개, 필수 답과 반환 근거를 함께 충족한 것은 14개였다. 상태·JSONL 수정은 채택한다. 설계와 근거는 [구현 설명](../../../docs/reference-claims.md)에 있다.

| 자료 | 한 번에 답·근거를 쓰는 joint | 근거를 먼저 고르는 claims |
|---|---:|---:|
| 기존 20문항, 답과 근거 | 19/20 (이전 평가) | 14/20 |
| 이전 진단 12문항, 답과 근거 | 9/12 (이전 평가) | 7/12 |
| 순서만 바꾼 한 문서, 양쪽 값 / 근거까지 | 1/2 · 1/2 | 2/2 · 1/2 |
| Ever 개발 10문항, 답 / 근거까지 | 2/10 · 2/10 | 2/10 · 1/10 |
| Wiki 8문항 × 3조건, 답 / 근거까지 | 12/24 · 11/24 | 12/24 · 11/24 |
| Wiki 두 문단을 함께 준 8문항, 양쪽 답과 근거 | 2/8 | 2/8 |

기존 경로 `attributed`의 과거 기준은 20/20, 진단 7/12다. 기존 32건에서 새 후보만 같은 검색 문단으로 추론했다. 과거 채점은 반환한 원문 문단의 지지를 인정했다. 새 후보는 좁힌 구절 자체를 호출자에게 근거로 돌려주므로 과거 점수와의 차이에는 답의 손실과 근거 범위의 손실이 모두 포함된다. 상태 수정만 적용한 기존 경로의 저장 출력 재생에서는 답과 근거 20개가 보존됐고 인용 미완료 8개가 partial로 표시됐다. ## 어디에서 답이 달라졌나

- **정답을 읽고도 반환하지 못했다.** Git notes 문항에서는 첫 단계가 manual을 찾았지만 모델이 JSON 문자열에 탭을 그대로 넣어 파싱에 실패했다. PEP 618에서는 ValueError를 찾고도 원문 코드의 백틱을 생략해서 근거 연결이 실패했다. Wiki 12에서도 두 생년월일이 원출력에 있었지만 탭 때문에 두 방식 모두 쌍 입력에서 빈 답을 돌려줬다.
- **양쪽 값을 보존해도 설명의 근거가 빠졌다.** 순서 비교에서 매뉴얼의 false와 실험 기록의 true는 두 순서 모두 살아남았다. 역순의 false에 붙인 구절은 “Defaults to false.”뿐이었다. 동일 원문 안에 다른 설정도 있어서 사용자는 이 구절만 읽고 어느 설정의 기본값인지 결정할 수 없다.
- **작성자 한 건은 복구했다.** 새 후보는 `@Noah`에게 보낸 기록의 작성자를 Mira로 답하고 해당 구절을 연결했다. 반면 local/CI 절차에서는 두 설정 이름만 찾고 실제 경고 후 계속/중단하는 동작의 근거를 빠뜨렸다.
- **검색과 독해가 서로 다른 지점에서 실패했다.** Ever의 45일 문항에서 top8에 12월 8일의 다음 작업이 없어 joint는 보류했고 claims는 1일을 추정했다. 반대로 약 복용 체크인 담당자 문항은 검색된 완료 보고의 작성자가 실제 정답 Hanqiang Liang이었는데도 한쪽은 이름을 생략하고 다른 쪽은 수신자를 담당자로 골랐다.

## 원래 벤치마크별로 본 결과

Ever의 두 독해 방식에는 각 질문에 동일한 BM25 top8을 줬다. 10문항 중 7문항에서 native R 위치 하나 이상을 회수했다. 전체 R 290개 중 22개(7.6%), 문항별 회수율 평균은 11.9%다. 한 질문의 R에는 주변 발화도 포함된다. 검색 실패의 의미는 해당 답을 결정하는 시점·조건이 실제로 입력에 들어왔는지 문항별로 확인해야 한다.

| Ever 유형 (각 2문항) | joint 답 / 근거까지 | claims 답 / 근거까지 |
|---|---:|---:|
| 단일 회상 | 1 / 1 | 1 / 0 |
| 다단계 | 0 / 0 | 0 / 0 |
| 시간 | 0 / 0 | 0 / 0 |
| 갱신 지식 적용 | 0 / 0 | 0 / 0 |
| 과거 맥락 선제 활용 | 1 / 1 | 1 / 1 |

객관식 4문항 중 요구한 선택지 글자로 답을 시작한 횟수는 joint 4건, claims 0건이다. 본문의 답 정확도는 선택지와 의미가 일치하는지도 인정한다. 금융 매핑 문항의 claims는 C의 내용과 실제 근거를 반환해 의미 점수는 통과했다. Confluence 문항은 양쪽 모두 목적지를 맞혔고 첫 원문에 검증 작업과 업로드가 함께 있었다. claims가 돌려준 짧은 구절에서는 어떤 보고서의 업로드인지 식별할 수 없었다.

| Wiki 조건 (각 8문항) | joint 답 / 근거까지 | claims 답 / 근거까지 |
|---|---:|---:|
| 첫 문단만 | 5 / 4 | 4 / 4 |
| 둘째 문단만 | 5 / 5 | 6 / 5 |
| 두 문단 함께 | 2 / 2 | 2 / 2 |

쌍 입력에서 두 방법이 모두 통과한 것은 교도소/구치소의 서로 다른 설명(222번), 선거 득표율 40.4%/약 57–58%(50번)이다. 원자료에도 해석상의 제약이 있다. 204번은 두 문단이 공백을 제외하면 같은 벌금액을 명시하지만 native 답은 Yes/No다. 8번의 첫 문단에는 native 답인 Daily Worker가 등장하지 않는다. 195번은 유의미한 비율을 묻는 표현에 <15%를 함께 써서 25%라는 출처와의 비교 방향이 모호하다. 모든 행과 기준 답을 그대로 포함해 채점했고, 원문 검토 이유를 따로 남겼다. 개발에 참여한 AI가 104개 출력을 검토했으며 독립 평가자 간 일치도는 측정하지 않았다. ## 실행과 판단

120046은 Slurm COMPLETED, 종료 코드 0:0, 프로그램 완료로 확인했다. 입력·코드·채점기 해시를 검사했고 104개 출력에 걸친 164개 실제 요청을 재생해 답과 인용 위치를 검증했다. 첫 실행 120041에서 36개 출력/65회 호출을 보존했고, 원자료의 빈 대화 그룹 처리 수정 후 120046에서 남은 68개 출력/99회 호출을 생성했다. 출력 한도에 걸린 호출은 0건이다. 데이터 점검 53초, 실패한 첫 실행 562초, 재개 실행 399초를 합쳐 GPU 1개 기준 **16.90 GPU분**을 사용했다. 유료 모델 API 호출은 0회다. 외부 두 데이터셋의 34개 입력 조건에서 joint는 34회, claims는 65회 호출했다. [실행 장부 대조](completion.json) · [호출·토큰·검색 통계](verification.json)

고정한 네 가지 채택 조건을 모두 충족하지 못해 이번 후보의 전면 교체와 확대 실행을 종료했다. 올바른 답을 근거 복사 실패로 막는 사례와 정답의 시점·조건 문단이 애초에 검색되지 않은 사례는 별개의 문제로 남는다. 원래 연구 비교군은 SpeakerMem-R1이다. 이번 실행은 개발 표본의 QA 독해 비교이며, 최종 Ever 876문항과 병합·승인 평가는 별도 단계다. [의사결정](summary.json) · [원래 평가 범위](../../../docs/evaluation-coverage.md)
