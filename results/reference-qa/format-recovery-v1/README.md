# 인용 형식 복구와 EverMem 입력 진단

2026-11-07 정리. `claims-v3`의 고정 104개 출력을 재생하고 새로 필요한 최종 생성 5회만 같은 Qwen3-8B로 실행했다. 답과 필수 근거를 함께 복구한 출력은 7개이며, 이전 성공 48개는 모두 보존됐다. `claims`의 기존 20문항 성과는 14/20에서 17/20으로 늘었다. 선택 경로는 `attributed`를 유지한다.

## 바꾼 부분과 근거

두 후보 `claims`와 `joint`가 쓰는 [형식 처리](../../../team_memory/reference_format.py)를 공통 함수로 모았다. 프롬프트, 검색 결과, 모델, 질문, 정답 키는 고정했다.

- JSON 문자열 안에 복사된 탭·줄바꿈은 Python 표준 `json.loads(..., strict=False)`로 읽고 동일한 Pydantic 스키마로 다시 검증한다. 미완성 JSON, 잘못된 스키마, 나머지 원시 제어 문자는 계속 거절한다. 실제 모델 원출력은 보존한다. [Python JSONDecoder](https://docs.python.org/3/library/json.html#json.JSONDecoder)
- RST 일반 문단의 짝지어진 인라인 리터럴 표시가 인용에서 빠진 경우 원문 위치가 유일할 때만 복원한다. 반환 근거는 원문을 직접 잘라 만든다. 단어·대소문자·코드 연산자 차이는 허용하지 않는다. Docutils의 인라인 리터럴 문법을 제한적으로 적용했으며 전체 파서를 가져온 것은 아니다. 들여쓴 코드, 지시문, 중복 위치, 일부 백틱만 남긴 출력은 이 경로에서 복구하지 않는다. [Docutils 인라인 리터럴 명세](https://docutils.sourceforge.io/docs/ref/rst/restructuredtext.html#inline-literals)

이는 기존 Attribute First의 구절 선택→주장 생성과 LangChain의 구절·출처 스키마 사이에서 문자열을 읽고 원문 위치를 연결하는 수정이다. 의미 판정기나 추가 모델 단계를 넣지 않았다. [기존 설계와 적용 범위](../../../docs/reference-claims.md)

## 실행 증거와 비용

Aurora 작업 `120074`는 GPU 1개와 conda 환경에서 실행됐다. 회수된 Slurm 기록은 `COMPLETED/0:0`, 프로그램 상태는 `complete`다. 고정 source·config·입력 해시와 실제 5회 요청을 대조했다. 모델은 같은 Qwen3-8B, 비사고 모드, temperature 0이다. 총 입력 2,897토큰, 출력 352토큰이며 유료 외부 모델 호출은 0이다. 모델 준비를 포함한 실제 사용량은 6분 22초, 6.37 GPU분이다.

## 채택 범위와 남은 문제

형식 처리 수정은 두 후보에 유지한다. `claims`는 여전히 기존 답·근거 3개를 잃으므로 `attributed`를 대체하지 않는다. 남은 사례에는 일부 백틱만 보존한 인용, 관계를 설명하지 못하는 짧은 구절, 원문 대소문자를 바꾼 구절이 포함된다. 이 결과를 본 뒤 허용 규칙을 추가하지 않았다.

다음 개발의 초점은 사람·사건의 연결과 기본 규칙·예외 규칙을 함께 검색하는 것, 그리고 이미 들어온 날짜·작성자·조건을 구절 선택에서 보존하는 것이다. 이번 진단으로 검색 설계 변경의 효과를 확인한 것은 아니다. 새 검색이나 reader 실험은 추가하지 않았다. 이 결과는 이미 본 개발 출력의 수정·회귀 진단이며 전체 벤치마크, 자동 재검토, 승인·병합의 해결을 뜻하지 않는다.
