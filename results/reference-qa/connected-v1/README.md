# 근거 계획·누적 검색 연결: 개발 비교 결과

2026-11-07. 새 후보는 EverMem 개발10문항에서 답·근거3/10으로 같은 실행의
단순 joint2/10보다 한 문항 높았다. 기존20문항은18/20으로 기존 선택 경로의
20/20을 보존하지 못했다. `connected`를 기본 경로로 채택하지 않는다.

## 구현과 의도

[설계](../../../docs/reference-connected.md) · [구현](../../../team_memory/reference_connected.py)

- Attribute First의 근거 묶음→문장 연결을 적용해 첫 호출이 구절 선택과 근거 계획을 함께 수행한다.
- IRCoT의 중간 정보→추가 검색→근거 누적 의도를 한 라운드로 제한해 적용한다. 별도 질의 생성 호출을 없앴다.
- 최초 top8을 버리지 않고 필요한 검색 결과를 최대8개 더한다. 선택 누락이 원문 삭제로 이어지지 않는다.
- 두 번째 호출은 계획과 원문 전체를 읽어 AQA의 출처별 답을 생성하고 기존 QuotedAnswer 인용 구조로 반환한다.
- 단계 지시를 system 메시지, 질문·원문을 user 데이터로 분리했다. 출처 번호는 검색 전후 동일하다.

이것은 원 논문 모델·학습·few-shot 전체의 재현이 아니다. 중간 계획의 의미적
정확성을 코드가 보장하지 않으며, 원문 전체를 남겨도 모델이 모두 활용한다는 보장은 없다.

## 남은 문제와 연결 판단

기존20의 두 실패는 `NAME := expr`만 남기고 `NAME <- expr`를 버린 사례와
`LengthMismatchError`만 남기고 `ValueError`를 버린 사례다. 두 사례 모두 계획부터
한쪽 답만 골랐다. 최종 생성기에 양쪽 원문을 남겼는데도 같은 누락이 이어졌다.
원문 전달 손실을 없앤 것과 대안 판단을 보존한 것은 다르다.

반면 작성자 Lizhen Zhou를 @수신자로 바꾸던 기존 오류는 이번 새 독해에서 복구했다.
Ever 담당자 문항은 독해만 바꿨을 때 실패하고 추가 알림을 찾았을 때 성공했다.
두 사실을 같은 원인으로 단정하지 않는다.

새 검색의 네이티브R 위치 회수는22/290→30/290이다. 이전 contextual도30이었지만
찾은 기록은 다르다. 이번에는 polling 정책을 직접 복구했고 P0 예외 일부도 찾았다.
그러나 최종 답이 인용과 반대이므로 검색 성공을 QA 성공으로 계산하지 않았다.
초기 계획이 답을 유도했을 가능성은 있지만, 계획을 제거한 동일 추가 문맥 대조는
하지 않았으므로 인과 원인으로 확정하지 않는다.

새 후보의 계획·최종 답 JSON 파싱 실패는0건이다. 다만 S3 계획의 인용 위치 오류
1건이 공유 계획을 사용하는 두 arm에 남았다. 파싱 성공·문자열 일치가 의미 정답을
보장하지 않는다는 점은 polling 사례에서 직접 드러난다.

## 결론과 범위

기존 선택 경로 `attributed`를 유지하고 `connected`는 실험 후보로 남긴다.
단계 간 원문/출처 보존은 고쳤고 작은 QA 개선은 측정했지만, 기존 정답 전체 보존과
상충 판단의 안정성은 달성하지 못했다. 이 결과를 보고 새 프롬프트나 실험을 추가하지 않았다.
이미 본 작은 개발셋이며 legacy 검색 입력은 고정이다. 전체 EverMem 성능,
새 사례 일반화, 승인·병합·자동 재검토의 성공을 의미하지 않는다.
