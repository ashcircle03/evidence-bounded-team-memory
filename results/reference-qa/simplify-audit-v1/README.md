- joint 기존20개 중 좁힌 인용 구절이 모두 원문 위치에 복원된 문항은13개다. 나머지7개는 원래 입력 문단으로 반환했다. 복원된13개 중에도 PEP680의 추가 tomli 구절과 Confluence의 Freemium 전략 구절은 해당 주장에 부적절하다. 위치 일치와 의미 지지는 다른 검사다. 이를 사후에 새로운 공식 점수로 바꾸지는 않는다.

## 2. 중요한 설계 결함: 검증 단위가 맞지 않는다

| 단계 | 실제 판단 단위 | 확인된 손실 |
|---|---|---|
| ConflictScore 연결 | 전체 초안 대 원문 문서 | rebase 답 안의 맞는 문장과 틀린 문장을 하나의 SUPPORTS 판정으로 통과시켰다. |
| AQA 실행 조건 | 인용한 원문 ID 집합 | 같은 원문에서 한쪽 주장을 인용하면 다른 쪽 주장이 빠져도 `missing_opposing_sources=[]`다. |
| 인용 추가 | 번호 없는 문장 | 이미 번호가 있는 문장에서 다른 근거가 누락된 문제를 검사하지 않는다. local/CI의 설정 조건 문서만 인용하고 실제 동작 문서는 빠졌다. |

`new-conflict-one-source`는 문서 판정이 CONTRADICTS인데도 최종 답에 같은 원문 ID가 있다는 이유로 AQA 재검토 대상이 비어 있다. 필요한 것은 원문 하나를 인용했다는 확인을 넘어, 답에 필요한 서로 다른 주장과 그 근거가 보존됐는지를 확인하는 것이다. 현재 연결은 그 책임을 구현하지 못했다.

새12개의 동일 실행에서 이미 저장된 초안과 최종 답을 사후 원문 채점하면 **6/12→7/12**다. 후속 단계는 서로 다른 문서의 두 상충 사례를 복구했고, 작성자 정답 Mira를 Git documentation·Eli까지 추가한 오답으로 바꿨다. 총51회는 초안12·문서 판정27·재작성5·인용7회다. 이12개에서 AQA 보정 호출은0회였다. 이 분석은 기록된 단계의 효과를 보여주며, 사전 등록한 별도 ablation 결과는 아니다. [문항별 단계 검토](stage-review.json)

## 3. 새로 재현한 구현·통합 문제

### P2: 단계 실패 상태가 일관되게 유지되지 않는다

`reference_quotes.py:87-99`는 잘못된 JSON 또는 다른 fact 목록을 내부에서 잡고, 기존 답을 다시 포맷하여 `status=ok`를 남긴다. `quote_attribution_error`·`attribution_status=partial`에는 오류가 있지만 공통 `stage_failures`에는 없다. 실제 이전20개 중4개, 새 attributed12개 중1개에서 관찰됐다. `docs/reference-joint.md`의 “부가 단계 실패 시 partial과 stage_failures” 설명은 이 경로를 포괄하지 못한다.

더 직접적인 상태 손실도 재현했다. `reference_attributed.py:51-58`에서 이전 문서 검토에 ERROR가 남아 있는 partial 결과를 AQA가 수락하면, 새 후보의 `ok`와 빈 warnings로 교체한다. 기존 ERROR 판단은 메타데이터에 남지만 최상위 미완료 상태가 사라진다. 이 두 번째 경로는 오프라인 오류 주입 재현이며 실제44개 실행에서 발생했다고 주장하지 않는다.

조치: 오류/미완료의 공통 상태 계약을 정하고, 보정 성공이 이전 검토 실패를 지우지 않도록 해야 한다. 정상 답을 보존하는 예외 wrapper만으로 모든 실패 경로가 처리되지는 않는다.

### P2: 원형 판정기의 오류 출력이 JSONL 응답 통로에 섞인다

`_vendor/conflictscore/eval_all_calibration.py:65-67`은 모델 호출 예외를 자체적으로 잡고 표준 출력에 일반 문자열을 쓴다. 실제 원형 함수를 통과시키며 타임아웃을 주입했더니 답은 partial로 보존됐지만 `Error evaluating document support: ...`가 stdout에 출력됐다. JSON 한 줄을 응답 하나로 기대하는 연결에서는 비JSON 행이 생긴다.

기존 검사 하나는 판정 함수 자체를 예외로 바꾸어 원형 함수의 내부 예외 처리·출력을 통과하지 않았다. 조치: 응답 스트림과 진단 스트림의 분리 및 실제 vendor 오류 경로의 계약 검사가 필요하다. 동시 판정이 있으므로 전역 stdout을 임의로 바꾸는 해결은 피해야 한다.

### P2: 문서 판정의384토큰 설정은 실제 요청에 적용되지 않는다

`reference_checked.py:121`은 `llm.chat(..., max_tokens=384)`를 호출한다. 설치된 OpenAILike/OpenAI의 `_get_model_kwargs`는 인스턴스 `max_tokens=1024`로 이 값을 덮어쓴다. 실제 기존 판정89회와 새 판정27회 모두 HTTP 요청은1024였다. 이번 출력 최댓값은 각각339·370토큰이며 실제 결과가 잘리거나 승인된 전체 예산을 넘지는 않았다.

조치: 어댑터 수준에서 실제 요청에 적용되는 설정을 사용하고 HTTP 본문으로 검증해야 한다. 현재 결과의 비용은 실측치여서 그대로 유효하지만, 소스의 호출 인자만으로 세부 자원 제한을 주장할 수 없다.

## 4. 실험 설명 정정: 순서만의 효과는 분리하지 못했다

정방향 입력에는 `Synthetic appended test report:`, 역방향에는 `Verbatim manual excerpt:`라는 서로 다른 제목이 있다. 공백과 위치도 함께 바뀌었다. 따라서 **두 변형에서 답이 달랐다는 관찰은 맞지만, 순서만 때문에 달라졌다는 인과 결론은 아직 성립하지 않는다.** 이전 보고의 순서 민감성 표현은 이 범위로 제한한다.

두 입력 모두 양쪽 주장을 보존해야 한다는 고정 요구사항과 전면 교체 보류는 여전히 유효하다. 새로운 순서 효과 실험을 한다면 문단과 제목·메타데이터를 그대로 유지하고 배치만 교환해야 한다. 이번 감사에서 원래 입력·정답·점수는 변경하지 않았다.

## 5. 레퍼런스 적합성에 대한 재평가

[AQA](https://aclanthology.org/2024.emnlp-main.956/)는 상충하는 출처의 답과 인용이라는 목적에 맞다. 그러나 이 프로젝트는 원 논문의 prompting·finetuning 기준선 전체를 재현하지 않고, 출처별 응답 지침과 예시를 Qwen3-8B에 적용했다. 이 선택만으로 같은 문서 내 여러 주장, 작성자 식별, 결합 근거의 완전성이 확보된 것은 아니다.

[ConflictScore](https://arxiv.org/html/2606.26437v1)는 핵심 체계에서 원자적 주장 분해를 사용하고, 일부 지지도 허용한다. R-RAG 사례 연구는 TruthfulQA의 이진 선택 설정이며 정답을 오답으로 바꾸는 harm rate도 보고한다. 우리 전체 자유서술 답을 문서 하나당 한 번 판단하고 재작성하는 연결은 원 논문의 모든 검증을 옮긴 것이 아니다. 이 차이를 알고도 모델이 알아서 보완할 것으로 기대한 부분이 남았다. 논문의 존재는 사용 이유이며 우리 요구 충족의 증거를 대신하지 않는다.

LangChain의 스키마와 fallback은 각각 출력 구조·예외 처리에 도움을 준다. 답의 완전성·주장 의미의 지지 여부는 별도 책임이다. 현재 문제는 공개 구현을 안 가져온 것만이 아니라, 서로 다른 단위와 전제를 가진 구현을 연결하면서 빠진 책임을 일반적인 프롬프트가 대신할 것으로 둔 데 있다.

## 6. 다음 변경의 우선순위

1. 상태 전파·JSONL 분리·실제 토큰 설정을 먼저 고친다. 이는 추가 의미 모듈 없이 연결 계약을 바로잡는 일이다.
2. 답의 각 주장과 원문 근거의 대응을 공통 단위로 정리한다. 문서 ID 포함 여부로 주장 보존을 대체하는 gate는 해결되지 않은 것으로 취급한다.
3. 다음 비교에서는 필수 답의 보존, 주장별 인용 지지, 근거 없는 추가 주장, 실제 호출 비용을 분리한다. 동일한 고정 소스에서 pure-order 쌍을 구성하고, 새 독립 사례로 이전에 본20개와 구분한다.

기존 attributed는 회귀 비교 대상으로 유지하고 joint도 저비용 비교 대상으로 남긴다. 이번 감사만으로 어느 쪽도 최종 설계로 확정하지 않는다. 두 구성 모두 새로운 작성자·조건별 인용 문제를 실패했으며 원래의 과거 결정 재검토·승인·병합 성능도 이번 QA 감사의 밖에 있다.

이 감사는 원래 actor·입력·정답·점수를 변경하지 않았고 새 GPU/API 요청은0이다. 다음 수정은 별도 버전에서 이 결함을 해결한 증거와 함께 평가해야 한다.
