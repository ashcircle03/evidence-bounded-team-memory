# 선택 문단 주변에서 실제 실패 동작을 복구할 수 있는가

**일부 복구에 성공했지만 기본값 채택은 보류한다.** 개발 두 건 중 git fsck에서 실제 오류와 발동 조건을 함께 되찾았다. 새 Git 보고 5건에서는 직전 역할 검증 방식보다 근거 있는 제안이 0건에서 1건으로 늘었다. 앞선 참조 방식도 다른 1건을 맞혀서, 그 방식에 대한 순증가는 없었다.

## 개발 두 건의 문맥 비교

이전 실험에서 선택된 과거 결정과 새 보고의 문단을 고정했다. 같은 Qwen2.5-3B-Instruct와 질문을 사용해 선택 문단, 앞뒤 한 문단, 앞뒤 두 문단, 다른 기록의 무관한 문단을 비교했다. FreeBSD의 실제 EACCES 설명은 선택 문단보다 두 문단 앞에 있으므로 두 문단 범위를 추가했다. 무관한 문단은 같은 분야에서 다른 작업을 다룬 기록이며 문서·화자·위치를 유지했다. 문단 수는 두 문단 확장 조건에 맞췄지만 글자·토큰 수를 정확히 같게 맞춘 실험은 아니다.

| 최종 방식에 제공한 문맥 | FreeBSD getcwd | 빈 파일의 git fsck |
|---|---|---|
| 선택 문단만 | 보류, 실제 실패 미복구 | 보류, 실제 실패 미복구 |
| 바로 앞뒤 한 문단 | 보류 | Invalid argument는 찾았으나 빈 파일 조건을 인용에서 누락 |
| 앞뒤 최대 두 문단 | 재검토를 제안했으나 실제 실패 미복구 | 빈 loose object 조건과 failed to read / Invalid argument 오류를 함께 복구 |
| 무관한 문단 추가 | 보류 | 보류 |

FreeBSD는 충분한 문맥 안에 EACCES와 작은 버퍼·권한 제약이 있었는데도, 큰 버퍼까지 재시도하라는 수정 방법을 골랐다. 실제 실패를 설명하는 구절을 선택하는 문제가 남았다. git fsck는 원래 문단이 오류 메시지를 소개하다 끝났고, 다음 문단이 실제 메시지였다. 두 문단을 함께 인용해 빈 파일에서 어떤 오류가 발생했는지 복원했다. 바로 앞뒤 한 문단만 추가해도 필요한 정보는 입력에 모두 있었다. 두 문단 범위로 넓힌 조건에서 온전한 후보를 선택했다는 점에서, 관측된 개선에는 후보 구성에 따른 선택 변화도 포함된다. [실제로 제공한 모든 구절과 최종 선택](development.ko.md)

처음에는 원래 QA 형식으로 문맥만 늘렸다. fsck의 오류 문자열이 일부 원출력에 나타났지만, 같은 문서의 여러 구절을 답한 것을 기존 QA 파서가 거절했고 설명은 과거 EMFILE과 현재 오류를 혼동했다. 두 번째 판은 이어지는 문단을 합치고 추출 형식을 완화했다. 오류는 더 잘 찾았지만 조건 질문에 오류 문자열을 다시 답했다. 첫 두 판의 엄격한 복구는 모두 0/2였다. 원출력과 모든 시도를 보존했다. [첫 판](development.json) · [두 번째 판](development-v2.json) · [최종 판](development-v3.json)

## 최종 수정

기존 선택기가 지목한 새 문단에서 앞뒤 최대 두 문단을 읽고, 각 문단과 바로 다음 문단을 연결한 후보를 만든다. 각 후보는 원문 안의 연속 구간이다. 같은 Qwen이 실제 관측 결과와 그 발동 조건을 함께 담은 후보를 고르며 근거 부족도 선택할 수 있다. 후보가 많으면 네 개씩 비교한 뒤 선택된 후보를 다시 비교한다. 각 비교에서 선택지의 위치와 글자를 회전해 평균 점수로 선택한다.

제안은 선택된 원문과 과거 결정의 원문으로 구성한다. 원 보고와 다른 문서의 구절은 재검토 근거로 발행하지 않는다. 저장된 제안에서는 원문 위치·화자·관찰 구절을 검증하고, 설명 뒤에 다른 주장을 덧붙인 경우도 거절한다. 의미가 맞는 구절인지는 별도 평가가 필요하다. FreeBSD와 ASan의 실패가 이 한계를 보여준다. [구현](../../team_memory/context_review.py) · [검증 테스트](../../tests/test_context_review.py)

## 새 Git 보고 5건

개발 결과를 반영한 코드를 고정한 후 새 보고의 양성 이력과 주제만 비슷한 결정 두 개가 있는 음성 이력을 비교했다. 방법별로 같은 모델과 최대 생성 길이 192를 사용했지만 호출 수와 문맥 길이는 다르다. 실제 모델 입력에 채점 기준이나 정답을 포함하지 않았다. [고정된 평가 기준](../../evaluation/context_review/PROTOCOL.md) · [동결 해시](../../evaluation/context_review/freeze.json) · [호출 수와 입력 길이](inference-costs.json)

| 실제 Git 원문에서 측정 | 앞선 참조 방식 | 직전 역할 검증 방식 | 새 문맥 확장 방식 |
|---|---:|---:|---:|
| 실제 대상에 재검토 제안 | 4/5 | 1/5 | 2/5 |
| 실제 오류와 조건까지 근거를 갖춘 제안 | 1/5 | 0/5 | 1/5 |
| 대조 결정의 다른 작업까지 구별한 제안 | 1/5 | 0/5 | 1/5 |
| 무관한 두 결정에 대한 오탐 | 0/5 | 0/5 | 0/5 |

- **git add -p 검색**은 새 방식이 복구했다. 네 hunk로 나눈 뒤 /Many를 실행했을 때 초기화되지 않은 $1 경고가 나고 검색식을 다시 묻는 로그를 인용했다. 앞선 참조 방식은 hunk가 하나뿐이었다는 잘못된 조건을 덧붙였고 역할 검증 방식은 보류했다.
- **ASan 초기화**는 실제 런타임 로딩 순서 오류를 복구했지만 SANITIZE=address로 컴파일한 조건은 선택 범위 바로 다음에 있어 누락했다. 따라서 엄격한 성공에 포함하지 않았다. 새 제안 2건 중 완전한 성공은 1건이다.
- **send-email 설정 우선순위**는 실제 전역·로컬 우선순위 오류를 충분한 관측으로 선택하지 못해 보류했다.
- **commit 권한 오류 중복**은 기존 결정 선택 단계에서 보류했다.
- **help의 단일 구획 앞 개행**은 참조 방식이 올바르게 설명했지만 새 방식이 보류했다. 새로 맞힌 건만 세면 이 손실을 놓치므로 순증가와 함께 기록했다.

무관한 결정 하나만 둔 음성에서도 새 방식의 오탐은 0/5였다. 원인 참조를 가린 양성에서는 세 방식 모두 0/5를 제안했다. 참조를 포함한 원문 양성·음성 10개에서는 후보 순서를 뒤집어도 새 방식의 결과가 동일했다. 같은 문서 안의 구절은 원래 순서로 정렬하므로, 개발 문단 순서 반전에서 일부 동일성은 구현으로 보장된다. 독립적인 사례 수는 새 보고 5개다. [문항별 판단·원문·설명](cases.ko.md) · [엄격한 의미 채점 근거](ratings.json) · [전체 집계](counts.json)

의미 판정은 방법 이름을 제거한 카드에 대해 한 평가자가 수행했다. 문체로 방법을 추정할 수 있고, 평가자 간 일치도와 통계적 일반화는 검증하지 않았다. ASan을 오류 문자열만 맞힌 부분 성공으로 포함하면 새 방식은 2/5가 되지만, 사전 기준의 발동 조건까지 요구한 주 성과는 1/5다.

## QA와 실제 Git pull

원래 배치 구성으로 136개 프롬프트를 다시 실행했다. 기존 성공 20개 항목에서 원래 파서를 통과한 답·상태·인용문·출처가 20/20 일치했다. 새 Git의 ASan·send-email QA도 pull 전후에 각각 SANITIZE=address와 ~/.gitconfig를 같은 근거와 함께 답했다. ASan에는 원 작성자의 승인을 기다리는 제안이 실제로 저장되어 있었다.

FreeBSD와 fsck도 별도의 Git 복제본으로 pull을 실행했다. 두 사례 모두 승인 대기 제안이 생겼고 QA는 원문 복제본과 정확히 같은 답·인용을 반환했다. FreeBSD는 EACCES, fsck는 EINVAL이었다. 즉 FreeBSD는 특정 사실을 묻는 QA에서는 올바른 실패 문단을 찾았지만 일반적인 재검토 관찰 선택에서는 그 문단을 놓쳤다. [기존·새 Git QA](qa.ko.md) · [개발 사례의 실제 pull 원출력](integration.json) · [통합 검사](integration-checks.json)

Aurora 119362, 119363, 119371, 119379, 119380, 119388의 여섯 작업은 모두 COMPLETED와 ExitCode 0:0, 완료 JSON이 일치했다. 이번 목표에서 GPU 11분 9초를 사용했고 누적 사용량은 127분 27초/150분이다. 짧은 작업의 Slurm MaxRSS 표본은 실제 최대 메모리를 충분히 측정하지 못할 수 있어 원본 값을 보존했다. 최종 제출 소스와 작업공간 소스를 바이트 단위로 대조했고 단위 테스트 60개가 통과했다. [작업별 자원·해시](runs.json)

실험 전략은 `python3 -m team_memory --store shared-records pull --model /path/to/Qwen2.5-3B-Instruct --strategy context-review`로 실행한다. 현재 결과는 문맥 확장과 관측 구절 선택이 일부 누락을 복구한다는 근거다. 일반적인 재검토 기준으로 채택하려면 이미 맞던 사례의 보존과, 완전한 오류 문맥 안에서 수정 방법과 실제 관측을 구분하는 능력이 더 필요하다.
