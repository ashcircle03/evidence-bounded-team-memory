# 결정 기록을 함께 읽으면 재검토와 QA가 나아지는가?

**판정** · 이번 Qwen2.5-3B-Instruct 실험에서 AI가 작성한 기록을 기본 입력으로 채택할 기준을 충족하지 못했다. 단일 답 QA에서 일부 답과 인용을 회복했지만 기존 정답도 잃었다. 재검토에서는 문서 순서에 따라 과거 근거 선택이 뒤집혔다. 원문에 결정 이유를 보존하는 방법의 효용은 이 판정기로 입증할 수 없었다.

## 비교 조건

A에는 동일한 과거 원문과 신규 원문을, B에는 여기에 과거 원문만으로 별도 작업에서 Qwen이 쓴 기록을, C에는 당시 Git 유지보수자 Junio C Hamano가 남긴 병합 메시지 발췌를 추가했다. 양쪽 과거 후보에 같은 방식으로 메모를 제공했다. 해당 근거는 고정해서 검색 실패를 제거했다. 메모가 추가돼도 원문은 잘리지 않았다. 모델 리비전·정밀도·읽기 한도·답변 지시·생성 한도는 조건 간 동일하다. 실제 입력 길이는 메모만큼 다르다. 모든 B는 과거 시점 재현본이고, 모든 C는 실제 당시 발췌본이다. 보지 못한 이후 결과나 평가 질문을 보고 원래 메모를 다시 쓰지 않았다. C에는 두 단어짜리 요약과 커밋 제목만 남은 사례도 있다. 같은 양식으로 위촉한 사람 Writer의 성능을 추정하는 실험으로 해석하는 데는 한계가 있다.

사전 고정한 원문과 채점 기준을 공개한다. Git 후속 커밋은 실제 기록이며 두 후보로 묶은 받은편지함은 재구성했다. 조건 대조 보고는 이 실험을 위해 작성했다. Aimers의 기존 메모는 사람 단독 작성 여부를 확인할 수 없어 A·B 진단에만 썼다. 양쪽 인용과 설명의 의미는 조건명을 가린 카드로 실험 수행 에이전트가 단독 판정했다. ## 재검토

첫 실행에서 재검토 53회 중 45회가 조치 필드에 예시의 문자열 `review or keep`를 그대로 출력했다. 출력 오류를 유지로 채점하지 않았다. 최초 14건의 필요한 알림은 A·B·C 모두 0/7이었다. 세 조건의 무효 응답은 13/14, 12/14, 12/14였다. 이 측정만으로 메모 효과를 판단하기 어렵다. [첫 판정 원출력과 인용](outcomes.json) · [첫 사건별 표](cases.ko.md)

후속 진단에서는 선택 가능한 조치와 실제 문단 ID만 출력하게 했다. Qwen이 조치와 두 문단, 설명을 선택했다. 자유 생성 설명을 포함한 71/71개 결과의 형식이 유효했다. QA는 다시 맞춰 조정하지 않았다. 최초 사건을 재생한 결과와 이 시점까지 읽기 평가에 사용하지 않은 후속 6건을 구분했다. 표의 적중은 재검토가 필요한 사건에서 대상·변경 이유·양측 근거가 모두 맞은 수다. 오탐은 유지해야 할 사건에서 재검토를 요청한 수다. - 분할한 패치에서 오프셋이 틀어지는 새 대조 사례에서 B만 과거의 ‘편집 후 분할하면 보정값이 사라진다’는 문단과 새 보고의 ‘분할 18/50 실패, 미분할 0/50 실패’를 함께 인용했다. 하지만 B는 별도 실제 Git 음성에서도 A와 C가 피한 오탐을 하나 더 냈다. [판독 변경 후 전체 사건별 실제 답·인용·채점](constrained/cases.ko.md)
- Aimers에서 B 메모는 원문 표의 MLP와의 상관계수 0.946을 MLP 성능 점수로 옮겼다. A·B 모두 재검토 조치를 냈으나 새 인용으로 성능 수치가 빠진 소제목만 골랐다. 이 사례에서 메모의 오류가 최종 판단 차이를 일으켰다고 볼 수 없다. [원문과 당시 사람 기록](../../evaluation/decision_records/frozen.json) · [Writer 원출력](writer.json) · [Aimers 두 답](constrained/cases.ko.md#aimers--prior_aimers)

### 원문 순서를 바꾸면

71/71회에서 인용한 과거 문서는 첫 후보였다. 판정기에 두 번째 후보도 출력할 수 있는 경로가 있는지 확인하기 위해 원문만 사용하는 A에서 문서의 표시 순서와 O1/O2 이름을 독립적으로 바꿨다. 서로 다른 네 사건에 네 조합을 적용했다. 번호만 교환하면 네 사건 모두 같은 문서를 유지했다. 순서만 뒤집으면 네 사건 모두 선택 문서가 바뀌었다. 첫 문서 선택은 **16/16회**였고, 첫 문서 이름이 O2인 8회에도 모두 O2를 골랐다. 내용과 관계없이 먼저 제시한 문서를 인용하는 경향이 이번 판독 조건에서 직접 재현됐다. 그 경향이 다른 모델·판독 방식에도 존재하는지는 별도 문제다. 기존 단일 답 16개는 Git 5개, PEP 8개, EverMem 개발 3개다. 과거 실행 중 하나라도 답과 인용이 함께 맞은 문항을 고정했다. 별도 복수 답 4개는 이전 합성 충돌·조건 평가에서 성공한 사례다. 복수 답에서는 출력 형식이 달라도 실제 양쪽 값을 각 근거와 함께 전달하면 인정했다. 미해결 표시까지 포함한 수치는 별도로 냈다. 이 실험의 QA는 같은 질문·정답을 새 받은편지함에서 읽는 근거 보존 시험이다. 다른 분야의 Git 결정이 함께 들어간 문항도 있으므로 원래 벤치마크의 전체 시스템 성적과는 구분한다.

- B는 fetch의 기본 출력 양식을 A의 `compact`에서 `full`로 바로잡고 근거도 맞혔다. 병합 충돌 양식에서는 두 조건 모두 `zdiff3`을 답했지만 B만 설정 설명을 인용했다. 반대로 PEP 669에서 A는 `sys.monitoring`을 명시한 문장을 골랐고 B는 같은 답 옆에 `Motivation` 제목을 붙였다. 합계가 높아도 이 손실은 그대로 남는다.
- C는 EverMem의 맞춤 보고 차원 제안자를 Lizhen Zhou에서 Yu Su로 바꿨다. PEP 618의 `ValueError`는 맞혔으나 존재하지 않는 원문 ID를 인용했다.
- PEP 680에서는 모두 `tomllib`을 답하고 모듈의 공식 문서를 가리키는 지시문만 인용했다. 그 구절에 TOML 파서라는 설명이 없어 엄격 기준에서 모두 제외했다. 모듈 문서 포인터만으로도 근거를 인정하면 16개 중 A/B/C 각각 12/13/9개가 된다. 조건 간 손익은 바뀌지 않는다.
- 복수 답 중 기본 remote 이름의 상충 보고에서는 세 조건 모두 `origin`과 `upstream`의 원문을 인용했으나 미해결 상태를 명시하지 않았다. 담수·기수 카트리지는 B만 L-2와 B-8을 조건별로 맞혔다. 두 PEP 충돌에서는 세 조건 모두 한쪽만 전달했다. [단일 답 실제 답·인용](cases.ko.md) · [복수 답 문항별 표](multisource.ko.md) · [단일 답 점수와 손익](scores.json)

## 다음 판단

Writer 학습이나 QA 기본값 변경은 보류한다. 먼저 직접 인용하는 판정기가 동일한 원문 쌍을 양쪽 순서로 받았을 때 같은 과거 결정과 관련 구절을 선택할 수 있어야 한다. 각 과거 결정을 신규 기록과 개별 비교하는 방식은 이 실패를 겨냥한 후보지만 이 실험에서 검증하지 않았다. 다음 비교에서는 위치를 교차한 실제 Git 사건에서 양측 인용 적중, 음성 오탐, 기존 QA 정답 손실을 다시 측정한다.

## 실행과 재현

- Aurora의 계산 노드에서 1 GPU씩 순차 실행했다. 작업 119279–119284는 모두 COMPLETED, 0:0이고 반환된 모델 원출력의 job ID와 동결된 입력 SHA-256을 확인했다. 누적 GPU 할당은 511초(8분 31초)다. [작업·입력 해시·토큰·자원 기록](runs.json)
- 원본 판정 재생은 저장소 루트에서 `python3 -m evaluation.decision_records.report`를, 판독 변경 재생은 같은 명령에 `--secondary`를 붙여 실행한다. 복수 답은 `python3 -m evaluation.decision_records.multi_score`로 재생한다. JSON의 문항별 원출력과 출처로 개별 채점을 검토할 수 있다. 작은 단일 프로젝트 실험이며, 여러 사건이 같은 과거 결정을 사용한다. 독립 표본의 일반 성능으로 해석할 근거는 없다.
