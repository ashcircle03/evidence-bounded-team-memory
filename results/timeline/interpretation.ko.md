# 어떤 설계를 가져갈 것인가

**연구 기본 경로는 `direct`로 정한다. 원문·출처·구절 단위 정정·명시적 검토 상태를 유지하고, 자동 결정 인용 색인은 기본 경로에 추가하지 않는다.** 두 경로 모두 아직 자동 검토와 누적 QA의 신뢰성을 보장할 수준은 아니다. 이번 목표에서 구현·비교·설계 선택은 끝내고, 최종 사례에 맞춰 추가 실험을 이어가지 않는다.

## 측정 결과의 의미

| 같은 14B 모델, 같은 원문 접근권 | 직접 읽기 | 색인 추가 |
|---|---:|---:|
| 필요한 검토에서 정답 과거 기록 쌍을 지목 | 12/12 | 12/12 |
| 관계 종류와 설명까지 맞힌 검토 | 8/12 | 7/12 |
| 검토가 필요 없는 흐름에서 오탐 | 5/8 | 3/8 |
| 같은 보고가 반복됐을 때 불필요한 추가 제안 | 5/20 | 4/20 |
| 답·인용·조건·상태·종류를 모두 맞힌 QA 시점 | 111/140 | 111/140 |
| 자연 QA를 세 시점에서 반복 확인 | 55/60 | 57/60 |
| 승인된 정정 뒤 새 값 및 무관한 기존 사실 보존 | 4/4 | 4/4 |
| 모델 호출 | 220 | 320 |
| 입력 토큰 | 247,256 | 366,533 |

20개 흐름에서 7번씩 묻기 때문에 140개는 독립 문항 수가 아니다. 자연 질문은 원본 EverMemBench-Dynamic topic 02의 20개다. 원래 메시지·질문·정답은 변경하지 않았고, 선택된 메시지가 공식 근거 범위에 속하는지도 확인했다. 검토·승인 상황은 별도로 만든 합성 작업 기록이다.

필요한 검토의 과거 기록을 찾는 것과 올바른 관계를 설명하는 것은 다르다. 두 방식 모두 필요한 12쌍을 지목했지만, 같은 조건에서 값이 다른 네 사건을 모두 `conflict` 대신 `reconsider`로 분류했다. 따라서 8/12를 “12개 중 4개를 전혀 찾지 못했다”로 해석하면 안 된다. 재검토가 필요 없는 사건과 반복 보고에서도 제안했으므로, 후보를 많이 올리는 것만으로 성공이라고 볼 수 없다.

`unsupported_alerts`의 14/12는 음성 오탐만 세는 수치가 아니다. 직접 읽기의 14건은 잘못된 관계 종류 4건, 반복 보고 5건, 검토 불필요 흐름 5건이다. 색인의 12건은 각각 4건·4건·3건과 설명 근거 부족 1건이다.

## 같은 QA 총점이 가리는 문제

색인을 추가하면서 직접 읽기가 맞힌 시점 7개를 잃었고, 반대로 7개를 새로 맞혔다. 사전 조건인 “같은 QA에서 기존 정답을 잃지 않는다”를 충족하지 못했다.

잃은 7개 모두 원출력에는 올바른 출처와 답 값이 있었다. 5개는 두 답을 반환하면서 종류를 `single`로 붙여 검증에서 탈락했다. 나머지 2개는 원문과 대소문자가 다른 인용 또는 조건을 반환해 탈락했다. 최종 API는 이 경우 빈 답 목록과 오류를 반환한다. **이는 전달된 QA의 실패지만, 해당 사실을 검색하거나 이해하지 못했다는 증거는 아니다.** 원출력과 검증 결과를 분리한 [진단 JSON](diagnostics.json)을 남겼다. 이번 평가에서는 이를 자동 수정하거나 정답으로 재채점하지 않았다.

자연 QA의 `Client Credentials Grant` 응답 하나는 출처와 의미가 맞는데 정답 문자열의 일반 명사 `mode`를 생략해 고정 채점에서 실패했다. 이 표현 차이를 실제 지식 회수 실패로 해석하지 않는다. `around 89%`에서 `around`를 생략한 사례는 짧은 답의 불확실성 표현 누락으로 별도 구분했다. 인용에는 해당 한정 표현이 남아 있다. 원점수는 변경하지 않았다.

기록이 늘어날 때의 보존도 완벽하지 않다. 처음 맞힌 자연 질문 중 직접 읽기는 새 보고 뒤 1개를 잃었다가 반복 보고 뒤 회복했다. 색인은 새 보고 뒤 1개, 반복 보고 뒤에는 2개를 잃었다. 별도로 유지한 기존 **3B QA 20/20 보존**은 이전 경로의 호환성 증거이며, 새 14B 경로의 이 문제를 없애 주지 않는다.

## 색인을 기본값으로 채택하지 않는 이유

색인은 음성 오탐을 줄였지만, 엄격한 검토 성공 수와 QA 보존 조건을 충족하지 못했다. 호출은 45.45%, 입력 토큰은 48.24%, 호출 구간 경과 시간은 9.98% 늘었다. 작성 100회 중 34회에서 형식·인용 오류가 발생했고, 저장된 색인 묶음은 66개, 결정 항목은 54개였다. 따라서 “올바르게 작성된 구조화 기억이 가치 없다”는 결론도 내릴 수 없다. 이 비교는 자동 색인 작성 실패까지 포함한 현재 구현 전체를 평가한다.

Granite의 설명 1건은 판단 여지가 있다. 과거의 일반 lookup 측정에 large-dictionary 성능 문제를 덧붙였다고 보아 엄격하게 실패 처리했지만, 메모리 제약 변화라는 핵심 연결은 맞다. 이를 통과로 바꾸어도 검토 성공은 양쪽 8/12이고 QA 손실 7개는 그대로여서 선택은 바뀌지 않는다. [민감도 확인](sensitivity.json)에 원점수와 대안 판정을 모두 남겼다. 채점자는 구현한 AI이며 독립 평가자의 일치도는 측정하지 않았다.

## 유지·제외하는 구성요소

| 구성요소 | 결정과 근거 |
|---|---|
| 불변 원문·출처·인용 위치 | 유지. 실제 최종 40개 흐름·방식 조합에서 원문 손실 없이 Git 상태가 수렴했다. |
| 작성자 검토와 구절 단위 정정 | 유지. 승인된 정정 4건 모두 새 값과 같은 문서의 다른 사실을 보존했다. 검토 없는 승인 상태 승격은 없었다. |
| 클라이언트별 처리 위치 | 유지. 공유 Git 기록과 분리해 다른 AI의 처리 이력이 자신의 검토를 생략시키지 않도록 한다. |
| 원문 전체를 한 번에 읽는 비교·QA | 최소 연구 기준선으로 유지. 작은 기록 묶음에서의 선택이며 긴 기록의 검색 성능은 평가하지 않았다. |
| 자동 결정 인용 색인 | 기본 경로에서 제외. 실험용 `--mode indexed`와 실패 원출력은 재현을 위해 남긴다. |
| 과거의 여러 단계 의미 검증 모듈 | 새 최소 경로에 연결하지 않는다. 앞선 연구 기록은 보존한다. |

현재 CLI 기본값은 `direct`다. 승인자를 실제 GitHub 계정과 연결하는 인증, 동시 작성자의 복잡한 병합, 매우 늦게 도착한 과거 결정에 대한 재계산은 이 구현·평가 범위 밖이다. 모의 작성자 검토는 실제 사람의 정확한 판단을 측정한 것이 아니다.

실제로 기록된 모의 승인은 14회다. 같은 조건의 충돌을 다른 종류로 제안한 8회는 정해진 검토 사건과 매칭되지 않았다. 또한 Harbor와 Kite의 색인 방식은 타당한 가용성 변화 구절만 골랐으나, 모의 승인 조건이 새 측정값까지 인용하도록 요구해서 승인되지 않았다. 이 두 건을 제안 근거 실패로 세지는 않았다. `reviewed` QA는 검토 사건을 시도한 뒤의 시점이며 모든 사례에서 승인이 일어났다는 뜻은 아니다. 이 검토 모의 규칙도 실제 팀의 검토 행동과 다른 제한이다.

## 완료 증거와 남은 품질 문제

실제 Qwen 응답 **540개**를 원래 입력과 바이트 단위로 대조하며 bare remote와 두 Git 복제본으로 재생했다. 최종 원문 덮어쓰기·검토 없는 승인 상태 승격은 0건이다. 이번 목표의 실제 계산 사용량은 **103.45 GPU분**, CPU 전용 작업 경과 시간은 13초다. 모든 제출 작업은 정상 종료했고, 추가 추론이나 재시도는 하지 않았다.

이 결과가 뒷받침하는 것은 원문과 검토 상태를 보존하는 실행 가능한 최소 시스템 및 색인 미채택 결정이다. 자동 재검토의 오탐, 충돌 종류 분류, 출력 형식 때문에 유효한 답을 잃는 문제는 남아 있다. 자동 지식 갱신을 믿고 맡길 수 있다고 주장하지 않는다. 이후 개선의 우선순위는 이 실제 실패를 해결하는 출력 계약과 검토 판단이며, 이번 최종 사례에 맞춘 후속 패치는 만들지 않았다.
