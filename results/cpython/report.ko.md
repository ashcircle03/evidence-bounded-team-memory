# CPython 외부 프로젝트 평가 · GPU 작업 119252

**현재 판정은 단순 검색+Qwen을 비교 기준으로 유지하고 재검토 모듈의 채택을 보류하는 것이다.** 5개 목표에서 두 방식은 모두 ‘기존 판단 유지’를 골랐다. 사전에 고정한 대상 문서와 조치를 함께 맞힌 것은 단순 방식 2/5, 모듈 1/5였다. QA는 6문항을 9개 시점에서 평가해, 답과 인용이 함께 맞은 출력이 0/9였다.

작업 `119252`는 Slurm 계산 노드에서 GPU 1개로 실행했다. 요청 시간 5분, 경과 47초, Slurm 종료 상태 `COMPLETED`, 종료 코드 `0:0`을 결과 파일과 대조했다. Qwen2.5-3B-Instruct 리비전 `aa8e72537993ba99e69dfaafa59ed015b17504d1`, CUDA BF16을 사용했다. 계산 노드로 전송한 데이터와 입력 패킷의 SHA-256을 확인했다. GPU 응답 29개(조치 20회·QA 9회)의 입력 해시와 이를 처리한 최종 출력 24건을 재생해 모두 일치함을 확인했다. ## 무엇을 고정했나

CPython의 실제 초안 3건이 main에 처음 들어온 커밋마다 첫 부모의 번호 붙은 RST 제안 문서 전체를 모았다. 두 검색 방식에 동일하게 과거 문서의 번호·제목·상태와 본문 첫 1,800자를 주었고, 새 초안은 처음 160줄을 사용했다. 각 사건의 입력에는 이후 승인, 수정, 회고가 들어가지 않는다. 대상, 허용할 조치, QA의 정답·출처, 확대 및 보류 기준의 해시를 검색·모델 출력을 보기 전에 고정했다. 초안과 일부 공식 결정은 사례를 설계할 때 읽었다. 사건은 의도적으로 선택했으며 무작위 표집이나 독립 평가자의 정답은 아니다.

같은 사건에 목표가 두 개 있어도 검색 적중은 한 번만 셌다. 새 기록에서 URL과 명시적 PEP 번호 참조를 제거하고 검색해도 위 세 건의 첫 후보는 그대로였다. RST 본문 전체, 위원회 토론 전체, 사전에 한 번도 언급되지 않은 후보의 발견은 이번 지표 범위 밖이다. [순위 기록](ranks.json)

**주석 구현.** 모듈이 내놓은 결정 구절은 PEP 649 제목이다. 그 안의 ‘Deferred Evaluation’은 어노테이션을 나중에 평가한다는 기술 용어다. 작성자가 결정을 보류했다는 뜻으로 읽을 수 없다. 당시 원문에 있는 승인 상태와 749 작성자가 이미 구현을 시작했다는 설명은 재사용할 수 있는 별도 근거다. [최초 749 초안](https://github.com/python/peps/blob/0a803fec895c5dea8df5153a34b70b1aade7425a/peps/pep-0749.rst#L35-L51) · [위원회의 649 승인](https://discuss.python.org/t/pep-649-deferred-evaluation-of-annotations-tentatively-accepted/21331/43)

**Free threading.** 779 초안에서 성능 저하를 측정하고 공식 지원 단계와 기본값 변경 단계를 구분했다. BM25는 기존 단계 결정을 담은 703을 선택했다. 모듈은 JIT 빌드의 LLVM 요구사항을 다루는 774로 갔다. 원문을 확인하니 결정 구절로 뽑힌 문장 자체가 그 제안의 목적에 포함되지 않는 판단을 설명하고 있었다. [최초 779 초안](https://github.com/python/peps/blob/9d017fba9be887c8fe7f6737ef543eef8093f781/peps/pep-0779.rst#L124-L159) · [위원회의 기존 단계 결정](https://discuss.python.org/t/pep-703-making-the-global-interpreter-lock-optional-in-cpython-acceptance/37075)

**Lazy imports.** 두 방식 모두 690을 찾았다. 모듈은 기각 상태를 정확히 찍었지만, 기각 이유는 ‘Since’로 끝나는 동작 설명 한 줄에 연결했다. 위원회의 당시 기각문에는 생태계가 서로 다른 import 동작으로 갈라지는 문제와 테스트 부담이 실려 있다. 그 결정문은 PEP 파일 바깥에 있어 이번 고정된 검색 모집단에 들어가지 않았다. 출처가 없는 경우 이유 미기록으로 남기는지 평가하는 사례다. [최초 810 초안](https://github.com/python/peps/blob/fad5cd133d734096cda7d8d88d7daaac71fb4fde/peps/pep-0810.rst#L817-L835) · [위원회의 690 기각 사유](https://discuss.python.org/t/pep-690-lazy-imports-again/19661/26)

## QA의 답과 인용

후속 진단에서 9회 각각의 입력과 원출력을 대조하고, 같은 Qwen으로 입력 범위와 출력 지시를 바꿔 재실행했다. [0/9 원인 분석](qa-diagnosis.ko.md)

두 시스템이 공유하는 QA 경로를 한 번 평가했다. 과거 결정 3문항은 새 기록 전·후에, 새 기록 3문항은 업데이트 후에만 물었다. 아래 링크는 채점자가 당시 Git 원본에서 확인한 정답 근거다. 모델이 사용자에게 유효한 인용을 반환한 건은 없었다.

| 문항 | 정답과 해당 시점의 근거 | 새 기록 전 | 새 기록 후 |
|---|---|---|---|
| 지연 평가 주석 제안의 기존 상태 | 승인됨. [PEP 649, 5행](https://github.com/python/peps/blob/e73affad4803beb5d251d665f9bd0142d1c79209/peps/pep-0649.rst#L5) | 근거 부족 | 인용 오류. 563과 749의 문장을 상충한다고 제시했으나, 상태를 담은 649를 인용하지 않았다. |

사전 채점 기준은 답의 의미 단서·올바른 PEP·실제 원문 인용을 모두 요구한다. 원출력 6건은 `null`, 나머지 3건은 인용 검증 실패였다. 9건 모두 올바른 문서가 상위 3개에 있었고, 정답을 지지하는 표현이 실제 Qwen 입력의 해당 문서에도 남아 있었다. 주석 상태와 import 상태의 업데이트 후 원출력은 기대한 충돌 출력 형식도 지키지 않았다. 재검토 장부가 QA에 개입하지 않는 설정이므로 두 방식의 QA 승패를 가릴 수 없다. 업데이트 전 과거 정답은 0/3이어서 기존 정답 보존율의 분모도 0이다.

## 채택 기준 적용

모듈이 단순 1회보다 새로 맞힌 목표는 0개, 잃은 목표는 자유 스레딩 기본값 1개다. 서로 다른 두 사건에서 결합 정답을 새로 얻고 기존 정답 손실이 없어야 한다는 사전 확대 기준에 미달했다. 이 실험에서 ‘유지’는 팀의 현행 결정을 계속 적용하자는 선택이며, 재비교 근거를 요청하거나 기존 작업에 새 근거를 연결한 것으로 채점하지 않았다.

하나의 외부 프로젝트에서 선택한 3개 사건이며 사전 키는 설계자가 작성했다. 기존 비교 실험용 선택지를 거버넌스 결정에 대응시킨 영향이 있다. 독립 사람 검토는 아직 0건이다. [블라인드 검토 양식](../../evaluation/cpython/review.md) · [문항별 실제 판정·인용 감사](score.json)
