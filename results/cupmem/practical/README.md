# Practical CUPMem 최종 평가와 채택 판단

**현재 CUPMem 후보를 기본 경로로 채택하지 않는다.** 원문 저장·검색·한 번의 독해·작성자 검토 상태를 개발 기반으로 유지하고, native 기억 작성과 자동 재검토 판단은 실험 기능으로 보류한다. 구현과 이번 고정 평가를 마쳤으며, 팀 지식 재검토 문제를 해결했다는 의미는 아니다.

## 고정 비교 결과

두 경로는 같은 로컬 Qwen3-8B, 원문, 임베딩, 문맥/출력 제한을 사용했다. 단순 경로도 현재 독해 입력과 인용 처리의 약점을 공유한다. 아래 점수는 원형 CUPMem/STALE 또는 SpeakerMem-R1의 재현 성적이 아니다.

| 항목 | 단순 검색·독해 | CUPMem 후보 |
|---|---:|---:|
| 기존 QA: 답 내용 | 12/20 | 9/20 |
| 기존 QA: 답과 선택 인용 모두 | 7/20 | 7/20 |
| 새 흐름: 근거 있는 재검토 | 0/10 | 0/10 |
| 새 흐름: 대상과 reconsider 종류만 일치 | 5/10 | 7/10 |
| 음성 흐름: 불필요한 제안이 나온 사례 | 0/10 | 0/10 |
| 음성 흐름: 오류 없는 올바른 무제안 | 9/10 | 9/10 |
| 부가 QA: 답과 선택 인용 모두 | 11/20 | 11/20 |

기존 QA에서 단순 방식의 **답과 인용 모두 성공한 항목을 잃은 수는 0건**이다. 하지만 단순 방식이 내용만 맞힌 답을 잃은 항목은 3건이며, 두 경로의 절대 성적도 낮다. 따라서 QA 보존 조건 하나를 통과했다는 사실을 품질 보존 또는 문제 해결로 확대하지 않는다. 과거 다른 모델의 20/20과 구분한다.

개발에 이미 사용한 Cedar 흐름은 후보 QA 5/5, 무관한 입력의 제안 0건이다. 별도 bulk 개발 QA 2/2와 실제 JSONL CLI 예제도 통과했다. 이들은 기능 연결 증거이며 미관측 성능이 아니다.

## 관측된 실패와 의미

- **입력 구성:** 검색 구절을 전체 원문으로 확장하고 각 조각에 출처 메타데이터를 붙여 문맥 한도를 넘었다. PEP QA와 일부 Git 재검토가 실제 BadRequest로 종료됐다. 문서를 찾지 못한 실패와 구분한다.
- **적재 의존성:** native 적재의 timeout/실패가 원문은 남아 있는 QA까지 needs_rebuild로 막았다. 첫 PEP 작업의 프로그램 제한시간 실패도 그대로 집계했다.
- **선택 인용:** 정답이나 대상 결정을 찾고도 핵심 절 앞에서 끝나는 문장 조각, 제목, 과거 상황을 새 조건으로 선택했다. 문자 위치는 맞지만 주장·이유·조건을 지지하지 못한다.
- **설명:** Perforce에서는 새 제약과 해결책을 섞었고, three-way binary에서는 실패 동작과 이전 fallback 상황을 혼동했다. runtime-prefix 부가 QA에서는 서로 다른 기록 사이에 없는 인과관계를 덧붙였다.
- **평가 경계:** Windows 문서 변경은 correction/reconsideration 경계가 모호하고, end-of-options 부가 질문은 날짜를 묻는 것으로 읽힐 수 있다. 사후 정답 수정 없이 고정 점수를 유지했다. 이 두 항목만으로 광범위한 모델 한계를 주장하지 않는다.

반환된 원문 인용 인스턴스는 416/416개가 일치했고, 실제 명시적 검토 없이 승인된 최종 제안은 0건이다. 중복 인용도 포함한 인스턴스 수이며 의미적 지지율과 다르다. 음성에서 오류로 제안이 저장되지 않은 사례는 성공적인 기권이 아니다.

## 비용

| 항목 | 단순 | CUPMem 후보 |
|---|---:|---:|
| 실제 호출한 QA 수 | 40 | 30 |
| 처리 차단으로 호출하지 못한 QA 수 | 0 | 10 |
| 호출한 QA당 평균 모델 요청 | 1.00 | 1.00 |
| 호출한 QA 평균 응답 시간(초) | 8.88 | 5.86 |
| 호출한 QA 중앙 응답 시간(초) | 4.68 | 4.11 |
| 최종 평가 물리 모델 요청(미완료 적재 포함) | 60 | 1908 |

이 goal의 모든 개발·실패·연속 작업·CLI 검사를 포함한 실제 할당은 **194.10/240 GPU분**이다. 최종 평가에서 기록된 요청 1968회 중 사용량이 없는 요청 22회는 토큰 0이 아니라 미측정이다. 기록된 입력 6,229,865 / 출력 286,029 토큰은 이 미측정을 제외한 합계다. 미완료 작업 단계에 속한 요청 104회도 전체 요청과 GPU 비용에는 포함했다.

QA 9회에서 1회로 줄이는 호출 구조는 구현됐지만, 품질을 유지한 비용 개선이라는 결합 목표는 달성하지 못했다. 적재/QA/검토별 토큰·시간은 [summary.json](summary.json)의 cost.by_operation을 확인한다. 시간에는 저장·검색·임베딩 등 해당 연산의 작업이 포함되며, 최초 모델 기동은 전체 GPU 비용에 포함된다.

## 실행과 재현

[Python·JSONL 사용법](../../../docs/practical-usage.md)에서 `--strategy simple`을 명시한다. 현재 constructor의 기본값을 실험 도중 바꾸지 않았으므로 Python 호출도 strategy를 명시해야 한다. 긴 문서 처리는 아직 일반 사용 기준을 만족하지 못한다. 후보를 조사할 때만 `--strategy cupmem`을 선택한다.

```sh
python3 -m evaluation.cupmem.practical.score
python3 -m evaluation.cupmem.practical.report
python3 -m evaluation.cupmem.practical.audit
```

위 명령은 공개 저장소에 보존한 입력·실제 출력·명시적 판정을 집계/검사하며 새 모델 추론이나 서버 제출을 하지 않는다. [문항별 비교](cases.md), [원문 기반 판정과 실제 출력](scored-cases.json), [채택 결정](decision.json), [요구사항 감사](completion-audit.json)를 제공한다. 각 실행 하위 디렉터리는 원출력/요청 로그, 입력 해시, Slurm 기록, 기계 검사, 의미 판정과 파일 해시를 보존한다.

로컬의 고정 upstream·이전 자료 캐시를 포함한 검사는 223개 모두 통과했다. 별도 디렉터리에 공개할 파일만 내보내서도 위 집계·감사를 재현했다. 이 환경의 단위 검사는 204개 중 197개 통과, 7개는 upstream 또는 과거 원자료 캐시가 없어 명시적으로 건너뛰었다. [로컬 검사](tests.json) · [공개 파일만 사용한 검사](export-verification.json). 테스트 통과는 모델 정확도를 의미하지 않는다.

## 해석의 한계

- 새 20흐름은 독립적인 실제 Git 후속 기록 10개를 양성/음성으로 짝지은 통제 구성이다. 각각 과거 원문 2개를 가진다. 실제 협업 20건이나 긴 자연 이력 성능으로 부르지 않는다.
- 기존 QA는 실제 공개 Git/PEP, 통제 반례, 자연 EverMemBench-Dynamic QA가 섞여 있다. 자연 QA는 3문항뿐이며 corpus별 성적은 summary.json에 분리했다.
- 일부 Git 기록은 과거 commit을 명시한다. 후보 연결이 더 쉬울 수 있다.
- 의미 평가는 개발에 참여한 AI 한 명이 원문과 비교한 판정이다. 독립된 사람의 검증이 아니며 판정 이유를 공개해 재검토할 수 있게 했다.
- 첫 PEP 작업의 실패를 재시도로 지우지 않았다. 답이 생성되지 않았던 나머지 두 이력만 같은 제한으로 분리해 이어갔다. 원래 순서와 달리 연속 작업에서는 simple을 먼저 실행했으며 비용에 모두 포함했다.
- 중단된 첫 PEP 작업의 native gzip은 끝부분이 닫히지 않은 상태 그대로 보존했다. 완전한 native 추적 로그라고 주장하지 않는다. 별도로 보존한 물리 요청 JSONL 219개와 Slurm 비용을 사용했고, 마지막 프로그램 스냅샷의 115회와 구분했다.
- 새 최종 결과를 보고 실행 코드·프롬프트·정답을 수정하지 않았다. 다음 개발에서는 이 사례들이 이미 노출된 개발 자료임을 표시해야 한다.
