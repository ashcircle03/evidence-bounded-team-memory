# 비교기 교체와 실제 Qwen QA 연결 — 2026-11-08

**결정: 14B 전면 교체를 채택하지 않는다. 기존 Qwen3-8B 비교기와 입출력 경계 수정판을 유지한다.** 새 사례의 근거 있는 재검토는 0/4→3/4로 늘었지만, 상충·조건별 공존을 정정으로 오인하는 회귀가 생겼다. 기존 QA20의 핵심 답·필요 근거는 유지됐고, 정정·상태8은 8/8→7/8이었다. 올바른 재검토를 직접 공급해도 QA가 의미를 잘못 풀어 쓰는 별도 문제가 확인됐다.

이번 goal의 비교와 적용 판단은 완료했다. 시스템 전체가 완성됐거나 새 설계를 배포했다는 뜻은 아니다. 평가 입력·실행·채점 코드를 추가했고 운영 `team_memory/` 코드는 변경하지 않았다. 모델 학습·유료 API·추가 프롬프트 후보 실험은 하지 않았다.

## 무엇을 고정했는가

- 비교기는 **Qwen3-8B** `b968826d…`와 **Qwen2.5-14B-Instruct** `cf98f3b…`다. 세대·체크포인트도 다르므로 순수한 파라미터 수 효과가 아니다.
- 검색·원문·선택 구절 복원·제안 검증·작성자 투표·QA는 고정했다. 모든 QA는 Qwen3-8B다. 두 비교기는 31건에서 **동일한 system/user 문자열**, 온도0, 출력 한도1024를 받았다. 토크나이저가 달라 토큰 수는 같지 않다.
- 새 관계20건은 재검토·무관·정정·상충·공존 각4건이다. 재검토/무관의 네 쌍은 같은 과거 결정을 공유한다. 독립적인 자연 사건20건이 아니다. 기존 서비스11흐름은 별도 회귀 패널이다.
- 비교기의 실제 원출력을 수정 없이 서비스에 다시 넣고, 최초 비교 입력이 정확히 같은지 확인한 후 실제 8B QA를 실행했다. 잘못된 관계를 정답으로 교체하지 않았다. 승인은 가상의 원작성자 동작이며, 실제 만들어진 검토 제안에만 적용했다.
- 기존37 QA의 8B 기준은 직전 실제 실행120445다. 이번 8B의 기존11개 제안·영수증이 그 실행과 동일하고 운영 코드도 같음을 확인했다. 14B 경로에서는 기존37개를 새로 추론했다. 저장된 답을 QA 실행으로 세지 않았다.
- 구현한 AI가 원문과 답을 대조한 비독립 평가다. 새 입력·정답과 비교 기준은 결과 열람 전에 고정했다. oracle 세부 체크리스트 파일은 제출 후, 결과 열람 전에 작성했다. 주요 의미·인용 기준은 제출 전 프로토콜에 있었다. 이 차이는 숨기지 않는다.

## 1. 올바른 재검토를 넣으면 QA도 올바른가

writer/cache 두 사례에 올바른 제안을 공급하고, 승인 전후의 이유·상태를 각각 물었다. 총8문항, 실제39회 호출이다. 이는 비교기 성능이 아닌 **QA 연결 시험**이다.

| 관찰 | 결과 |
|---|---:|
| 최초 모델 입력에 올바른 재검토 효과·승인 상태 포함 | 8/8 |
| 과거 관측을 거짓으로 무효화하지 않음 | 8/8 |
| 요구한 의미를 모두 만족하는 답 | 2/8 |
| 재검토를 정정으로 잘못 설명 | 4/8 |
| cache 이유 질문에서 20초 삭제 조건 누락 | 2건 |
| 승인 의미를 직접 묻는 두 답에서 “검토 허가만” 구분 | 2/2 |

올바른 구조 데이터는 실제 첫 입력까지 전달됐다. 그런데도 최초 초안부터 “미승인 정정”, “재검토 승인을 받은 정정”으로 바꾸어 설명하거나, 새 정책30초와 캐시20초 중 후자를 버렸다. 인용 후처리에서만 생긴 문제가 아니다.

정답 의미를 만족한 승인 상태2개도 사실 설명에 원문을 직접 붙이지 않고 검토 스냅샷만 인용했다. 그래서 **원문 직접 인용까지 모두 요구한 엄격한 점수는0/8**이다. 스냅샷은 원문으로 추적 가능하므로 “근거가 전혀 없다”는 뜻과 구분한다.

## 2. 비교기만 바꾼 새20건

관계 종류와 선택 구절이 실제 변경 조건을 지지하는지 함께 봤다. 단순 JSON 파싱 성공률이 아니다.

| 항목 | 8B | 14B |
|---|---:|---:|
| 근거 있는 재검토 | 0/4 | **3/4** |
| 무관한 보고에서 정확히 관계 없음 | 0/4 | 1/4 |
| 명시적인 사실 정정 | 4/4 | 4/4 |
| 같은 조건의 상충 결과 보존 | **4/4** | 0/4 |
| 다른 조건의 공존 | **3/4** | 2/4 |
| 무관4건 중 불필요한 검토 제안 — 낮을수록 좋음 | 1/4 | 1/4 |
| 검증 실패 사례 — 정답 보류로 세지 않음 | 1 | 0 |

“관계 없음” 실패와 “불필요한 검토 제안”은 다르다. 무관한 보고를 참고용 공존으로 붙이면 관계 분류는 틀리지만 승인 요청은 만들지 않는다. 이들을 전부 검토 오탐으로 합산하지 않았다.

14B는 API 재개 기능, 메모리/정확도 조건 개선, 출입 허가 변경을 재검토로 구분했다. 반면 같은 조건의 독립 측정4건을 모두 정정으로 처리했다. 작업자1명/4명의 측정은 공존해야 하는데 정정으로 처리했고, 조명 조건 사례에서는 관계를 놓쳤다. 명시적 정정4건은 종류·대상 구절이 맞았지만 설명은 모두 프롬프트의 `specific claim, evidence and conditions`를 그대로 복사했다. 설명 품질까지 해결됐다고 볼 수 없다.

기존 writer/cache 양성2건은 14B에서도 유효한 재검토0/2다. writer는 정정으로 분류했고, cache는 재검토를 골랐지만 원문 ID를 잘라 써 검증에서 거절됐다. 알려진 무관2건의 불필요 제안은2→1개로 줄었다. 새3/4와 기존0/2를 함께 보고해야 한다.

## 3. 실제 제안 → 승인 → 같은8B QA

새 재검토4흐름을 각 모델의 실제 관계로 재생하고 승인 전 이유/승인 후 상태를 물었다. 총8문항씩이다. 재검토가 만들어지지 않은 흐름에 정답 제안이나 투표를 몰래 추가하지 않았다.

| 흐름 | 8B 비교기 경로 | 14B 비교기 경로 |
|---|---|---|
| API v2→v3 | 정정 승인 뒤 v2의 옛 관측이 틀렸다고 답함 | pending 설명은 맞음. 승인 후에는 사실 보존을 말하면서도 새 보고를 “정정”으로 부름 |
| 출입 허가08–18→22–02, 2주 | 승인 전 조건 설명은 맞지만 정정 제안을 생성 | **재검토 제안·승인 전후 QA 모두 성공**. 옛 사실 보존, 검토 허가만, 아직 관측하지 않았음을 명시 |
| 60개 중24개 비상업 동의 | 범위는 읽지만 정정으로 처리 | 공존만 생성. 투표가 없는데 QA가 Alex의24개 공개 승인을 지어냄 |
| 32GB→6.2GB, 8GB기기, 정확도92≥90 | 중복 후보 검증 실패. 투표가 없는데 승인했다고 답함 | 조건과 review-only 승인은 전달. pending 답에서 검토자 Alex를 제안 작성자로 잘못 지칭 |

14B 경로에서 핵심 답과 요구 설명을 만족한 것은5/8, 올바른 재검토까지 연결된 QA시점은4/8이다. **승인 전후 두 시점이 모두 충족된 흐름은1/4**다. edge는 조건 자체는 맞았지만 확인되지 않은 제안 작성자를 덧붙여 엄격한 성공에서 제외했다. 이 보조 평가를 완전히 독립적인 시스템 성공률로 일반화하지 않는다.

8B의 edge 답에 등장한 하늘·물 문장은 팀 기록이 아니라 실제 LlamaIndex `CITATION_QA_TEMPLATE`의 예제를 베낀 것이다. 해당 최초 요청과 응답은 call34에 보존했다. 또한 유효한 관계가 없으면 `active_review_context`가 없고, `review_errors`는 생성 후 반환에만 추가된다. 모델은 승인 질문의 전제를 그대로 받아들였다. 이는 실제 입력에서 확인한 연결 한계이며, 한 요소만 고치면 해결된다는 인과 검증은 아니다. 고정 비교 중에는 템플릿이나 서비스 코드를 바꾸지 않았다.

## 4. 기존 답·정정·상태 보존

| 평가 | 8B 기준120445 | 14B 비교기 +8B QA120453 |
|---|---:|---:|
| 기존20 핵심 답 + 필요한 근거 | 20/20 | **20/20** |
| 정정·상태8 핵심 답 + 상태 근거 | 8/8 | **7/8** |
| 위8에 엄격한 원문 직접 인용까지 요구 | 7/8 | 6/8 |

기존20 중13개의 원출력과 answer/evidence 객체가 정확히 같았다. 달라진7개도 원문으로 재채점해 정답과 필요한 근거를 확인했다. `grep.extendedRegexp`의 인접 문단 인용은 이전과 같으며 고정 키 위치19/20과 의미 지지20/20을 구분한다. 부연 문장의 모든 인용이 완벽하다는 뜻은 아니다.

새 회귀는 Cedar 승인 후 답이다. 승인된480MB와 옛500MB가 superseded라고 맞게 설명한 뒤, **마지막에 “For release Cedar, the upload cap is 500 MB.”라고 현재형으로 덧붙였다.** 실제 정정 제안·투표는 올바르므로 독해/후속 답 생성의 실패다. 이 단일 실행으로 14B가 통계적으로 항상 그 회귀를 만든다고 주장하지 않지만, 보존 기준을 통과했다고 할 수는 없다. 원출력과 상태 인용은 모두 남겼다.

## 적용 판단과 다음 설계상 제한

사전 기준은 재검토 증가, 오탐 비증가, 정정·상충·공존 각각 비퇴보, 기존QA20/상태8 보존, 올바른 재검토의 QA 전달이었다. 14B는 재검토를 개선했지만 다른 필수 기준을 통과하지 못했다. 따라서 기존 비교기를 유지하고 **학습이나 모델 확대를 해결책으로 확정하지 않는다.**

이번 결과는 두 결정을 지지한다. 첫째, 비교기 전체를 바꾸면 다른 관계의 기능까지 함께 바뀐다. 둘째, 코드가 이미 알고 있는 승인 사실과 효력을 QA가 다시 자유롭게 해석하는 구간이 남아 있다. 다음 수정 대상으로는 이 상태의 표현·연결 책임이 더 직접적이다. 이것은 이번 관찰에서 도출한 우선순위이며, 새 구조의 효과를 검증한 결과는 아니다. 추가 모델 호출이나 변형은 이번 goal에서 늘리지 않았다.

## 실행·비용·재현

모든 작업이 Aurora GPU 계산 노드·conda에서 Slurm12시간 상한으로 실행됐다. 노드를 지정하지 않았고 모두 `COMPLETED/0:0` 및 프로그램 complete, 입력/코드 해시, 원문·검토 스냅샷 인용 연결을 확인했다.

| 작업 | Job ID | GPU | 실제 경과초 | 실제 호출 |
|---|---:|---:|---:|---:|
| 올바른 재검토 QA | 120449 | 1 | 423 | 39 |
| 8B 비교기31건 | 120450 | 1 | 175 | 31 |
| 14B 비교기31건 | 120451 | 2 | 701 | 31 |
| 8B 새 흐름QA8 | 120452 | 1 | 195 | 36 |
| 14B 결과 재생 +8B QA45 | 120453 | 1 | 747 | 241 |

합계 **49.03 GPU분**, **378호출**, 입력522,538/출력68,975토큰이다. 모델 준비·노드 캐시 복사를 포함한 실제 GPU 할당 시간이다. 14B는 새 캐시 준비와 GPU2개를 포함하므로 동일 하드웨어 추론 속도 비교가 아니다. 과거 기준120445의 비용은 이번 합계에 재합산하지 않았다. MaxRSS는 각 `dispatch.json`의 batch/step 행에 보존했으며 빈 job행을0으로 해석하지 않는다.

```sh
# 각 완료 폴더의 Slurm/프로그램/입력/구절 연결 검증
python -m evaluation.comparator_choice.verify results/comparator-choice/oracle-v1
python -m evaluation.comparator_choice.verify results/comparator-choice/compare-8b-v1
python -m evaluation.comparator_choice.verify results/comparator-choice/compare-14b-v1
python -m evaluation.comparator_choice.verify results/comparator-choice/flow-8b-v1
python -m evaluation.comparator_choice.verify results/comparator-choice/flow-14b-v1
# 보존된 원문 기반 ratings의 집계. 자동 의미 채점기가 아님.
python -m evaluation.comparator_choice.compare
python -m evaluation.comparator_choice.decision
```

로컬 실행 계약 검사 `tests/test_comparator_choice.py`: 3tests/2subtests 통과. 기존 운영 코드 해시가 직전 경계 수정판과 같음을 확인했다. 14B 재생에서 기존 cache ID 오류1건, 8B 재생에서 새 edge 중복 오류1건은 숨기지 않고 failed receipt로 보존했다.

이 결과는 소수 합성 진단과 재사용한 회귀셋에 한정된다. 기존20에는 자연 EverMem3문항이 포함되지만, **EverMem/Wiki 전체 벤치마크 성과가 아니다.** 현재 모델을 실서비스 수준으로 완성했다고 선언할 근거는 없다.
