## 고친 부분

기존 LangChain `FactWithEvidence` 인용 단계에 실제 timeline 제안·작성자 투표로 만든
`review_state` 근거를 연결했다. 새 판정 모델이나 재시도 단계는 추가하지 않았다.
원문 근거와 검토 상태 근거를 구분하는 의도는 [설계 계약](../../docs/review-state-citations.md)에 있다.

120359에서 실패했던 pending/current 두 응답의 **답 문구와 기존 원문 인용을 유지**하면서
미승인·원기록 보존·승인 설명 세 문장에 정확한 스냅샷 인용을 추가했다.
120370에서 실제 Qwen2회 호출로 확인했다. 승인 인용은 원작성자의 실제 저장된 vote ID까지
연결되며, pending은 투표가 없는 시점의 스냅샷이다. 시각이 없는 기존 투표에 날짜를 만들지 않았다.
[검증](development-verification.json). 이는 다른 문장에 대한 상태 적용 정확성 보장이 아니다.

## 비교 조건

같은 Qwen3-8B·nonthinking·temperature0, 같은 입력과 최초 프롬프트를 사용했다.
43개 비교쌍의 최초 실제 HTTP 요청이 모두 같았다. direct에도 원문 검색·검토 상태·같은
인용 기능을 줬다. 차이는 attributed의 문서별 judge→필요시 답 수정→AQA 보완이다.

원본 데이터셋의 새 QA는 Ever03/04에서 고정 해시로 고른6문항, 이전 평가 ID를 제외한 Wiki6문항이다.
Ever는 전체 주제에서 BM25 top8/512/64로 검색한 같은 근거 묶음을 두 reader에 제공했다.
Wiki는 제공된 상충 문단쌍이다. 따라서 원본 데이터셋 QA 비교는 **동일 검색 결과의 reader 비교**이며
배포 hybrid 검색의 전수평가가 아니다. 합성8개 흐름에서는 실제 서비스의 검색·상태·QA를
11개 시점에 실행했다. 별도로 기존20문항도 같은 원문 묶음으로 새 추론했다.

| 핵심 답 + 필요한 근거 | direct | attributed |
|---|---:|---:|
| 새 EverMem6문항 | 2/6 | 2/6 |
| 새 WikiContradict6문항 | 1/6 | 3/6 |
| 새 합성8흐름의11개 QA시점 | 7/11 | 9/11 |
| 기존20문항의 새 동일근거 추론 | 17/20 | 20/20 |

이 표는 모든 부연 문장의 인용이 완벽하다는 점수가 아니다. required answer/evidence를
판정하고 상태 인용·부연 인용 오류는 별도 기록했다. 구현한 AI가 arm 이름을 가린 카드로
원문을 검토했으며, 독립 사람 평가가 아니다. 코드·입력 선택·기준은 새 출력 전 고정했고
실행 후 의미 규칙/프롬프트를 바꾸거나 추가 사례를 돌리지 않았다.

기존20의 **동일 응답 재생**도 답·근거20개 모두 그대로였다. 이는 위의 **새 추론**과 별개다.
재생은 draft20+후속112개 요청을 확인했으며 검색을 새로 실행하지 않았다.
[재생 결과](legacy-replay.json). direct가 잃은3건은 origin/upstream, `:=`/`<-`,
ValueError/LengthMismatchError의 상충 답 중 한쪽을 버린 사례다.

## 얻은 것과 남은 문제

attributed는 새23개 QA에서 필수 근거까지 성공한 답이4개 더 있었고, direct의 성공을
잃은 사례는 없었다. Wiki의 생일·어원 양쪽 답, 승인 이벤트 인용, 재검토 이유의 옛 조건
인용에서 차이가 났다. 따라서 추가 단계가 무의미하다는 결론은 맞지 않는다.

그러나 새 QA 호출은 **37→127회(3.43배)**, 측정된 QA 실행시간 합은105.55→298.72초였다.
사전 기준인 호출2배 이내를 넘었다. 공유 재검토 호출8회는 양쪽 QA 비용과 분리했다.
전체 비교는332회, 알려진 인용 수정2회를 합쳐 실제334회 모델 호출이다.

새 상태 질문에서는 양쪽 모두 다음 오류가 남았다.

- **미승인 정정:** pending 정보가 실제 입력에 있는데도 제안480MB를 현재값으로 말한다.
- **거절된 정정:** vote는 rejected로 저장됐지만 기존 `expand_review_context`가 rejected
  관계를 제외한다. 모델 입력에 거절 상태가 전달되지 않아 Tuesday를 현재값에 섞는다.
- **수정 범위:** Cedar correction은 바뀌지 않은 소유자Hana까지 old/new quote에 포함한다.
  정확한 문자열 인용만으로는 주장 범위를 올바르게 선택했다는 보장이 없다.

Ever 실패도 한 종류가 아니다. 다음 독립 작업의 기록이 top8에서 빠진2건, Web-IDE 완료
시점이 빠진1건, 시작·종료 정보가 있어도4근무일을5일로 계산한1건을 구분했다.
또한 추가 judge로 전달된 원문에 recorded_at이 빠져4월15일 진행 중/4월18일 완료를
충돌로 오인한 사례가 있다. 실제 요청8개에 두 날짜/recorded_at이 모두 없음을 확인했다.
judge12회는 고정384토큰 한도에서 잘려 ERROR로 남았다. 자원을 늘려 재실행하지 않았다.
이 결과는 **현재 구현·모델·출력 한도 조합**의 평가이며 설계 이론 자체의 반증이 아니다.

## 공유 재검토 생성

두 reader가 같은 timeline 비교 결과를 사용하므로 상대 성능 향상이라고 계산하지 않았다.

- 실제 이유가 바뀐 재검토2건: 둘 다 옛 결정·이유와 바뀐 조건의 원문을 찾았다.
- 주제만 비슷한 음성2건: 잘못된 reconsider는0건이지만, **불필요한 coexist 제안이2건** 생겼다.
-8개 업데이트 중 관계 종류/대상이 맞은 것은6건. 변경 범위까지 엄격히 보면5건이다
  (Cedar correction에 변경되지 않은Hana 포함).

[제안별 근거 검토](proposal-review.json). 합성 사례이며 비교 입력의 source location에
설명적인 사례 이름도 노출됐다. 이 수치는 진단용이며 실제 Git 재검토 일반화 성능으로
해석하면 안 된다. 모든 승인은 가상 작성자 fixture 동작이다.

## 설계 판단과 실제 적용

**원문·검토 기록을 보존하고 구분해서 인용하는 공통 부분은 유지한다.**

사전 규칙의 비용 기준으로는 direct가 잠정 후보지만, 기존20에서3건을 잃어 전면 교체
조건을 충족하지 못했다. 따라서 **기존 기본값 attributed는 호환성을 위해 유지**하고,
`--reader direct`는 비교/속도용 선택지로만 제공한다. 사례ID별 분기는 추가하지 않았다.
추가 judge/AQA 단계를 무조건 늘리거나 전부 삭제하는 변경도 하지 않았다.

현재 시스템이 승인 상태를 정확히 적용한다고 보장할 수 없다. 다음 개발의 우선순위는
추가 판정 단계보다 이미 존재하는 pending/rejected/승인 범위를 QA 출력에 제대로
전달·적용하는 경계다. 여기서는 고정 비교와 판단까지 끝내고 추가 실험은 중단했다.
[적용 판단 JSON](deployment-decision.json).
