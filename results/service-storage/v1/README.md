위 수치는 실제 ReferenceQA 경로의 MockEmbedding 계수이며 의미 검색 성능이나 실제 모델 속도 측정이 아니다. [변경 후 계수](lifecycle.json), [변경 전 계수](../audit.json). 질문 자체의 임베딩은 매 질문 1회다.

- source 패키지를 저장소 밖에서 실행한 서비스·상태 인용 검사 17개 통과. 계약 예제 24개 통과는 fixture-only다. [명령·결과](local-checks.json).
- 준비되지 않은 질문은 문서 임베딩/관계 sync 없이 INDEX_STALE. 문서 1개 추가·중복 입력·승인·재시작·게시 실패 복구를 검사했다.

## 실제 임베딩 비교 — 완료

Slurm **122918, COMPLETED / 0:0**, 프로그램 완료·입력·설정·코드 해시를 확인했다. RTX3090 GPU1, 총42분34초(42.57 GPU분), batch MaxRSS 1,006,696K. 실제 비용은 준비와 검증용 저장소 생성·정리도 포함한다. [검증 요약](verification.json), [Slurm 자원 기록](accounting.txt), [완료 장부](dispatch.json).

[고정 입력](inputs.json)은 기존7개 원문 집합과20개 질문이다. 집합별 중복을 포함해 원문1276개, chunk1414개다. 같은 embedding checkpoint·Qwen tokenizer·검색 설정으로 frozen `cabaf1f` 전체 구축과 새 준비 경로를 비교했다. [프로토콜](PROTOCOL.md), [설정](config.json), [사전 동결](freeze.json), [문항별 표](cases.md), [모든 순서 있는 근거](retrieval.json).

| 확인 | 결과 |
|---|---:|
| 기존 전체 구축 → 준비된 색인: 원문 ID·구절·위치·작성자·시각·순서 동일 | 20/20 |
| 새 reader 재시작 뒤 근거 동일 | 20/20 |

| 추가 후 증분 준비 → 확장된 같은 corpus의 전체 구축: 근거 동일 | 20/20 |
| 새 경로의 질문80회 중 문서 임베딩 | 0 |
| 7개 집합에 원문을 하나씩 추가 | 각1개만 준비, 총7개 chunk 임베딩 |
| 같은 입력을 다시 넣을 때 문서 임베딩 | 0 |

새 Qwen 답변 생성은 **0회**다. 검색 결과의 회귀 검사와 위 QA 기록 재생을 구분한다. 문서 추가는 각 corpus당 무관한1개 fixture이므로 임의의 새 관련 문서도 기존 답을 바꾸지 않아야 한다는 주장은 아니다. 재시작은 새 reader 인스턴스의 disk load, 실패 복구는 별도 로컬 테스트이며 실제 프로세스 강제 종료 실험은 하지 않았다.

## 시간 비용: 최초 대량 준비는 퇴행

아래는 같은 GPU 작업의 단계별 합계다. 대기·모델 초기화·검증용 원문 저장소 생성/정리는 제외되며, 반복 조회로 OS 캐시가 달라질 수 있다. 별도의 안정적인 지연시간 benchmark가 아니다.

| 단계 | 문서 chunk 임베딩 | 시간 합계 |
|---|---:|---:|
| 기존: 7개 cold corpus에서 첫 질문과 나머지 질문20개 | 1414 | 20.10초 |
| 새 경로: 질문 없이 초기 준비 | 1414 | 685.52초 |
| 새 경로: 준비 뒤 첫 질문 묶음20개 | 0 | 2.05초 |
| 새 reader 재시작 뒤 질문20개 | 0 | 3.46초 |
| 7개 corpus에 원문1개씩 추가·준비 | 7 | 23.51초 |
| 추가 후 질문20개 | 0 | 0.63초 |
| 중복 입력7회 준비 | 0 | 2.31초 |
| 같은 확장 corpus를 새로 전체 준비 | 1421 | 609.68초 |

**질문에서 무거운 일을 제거했지만 최초 준비 자체가 훨씬 비싸졌다. 전체 처리속도 개선으로 해석하면 안 된다.** 문서별 cache 영속 저장·fsync, 문서별 embedding batch, shared Ceph 파일시스템 등이 이전 bulk build와 다르다. 실행 중 Ceph metadata request 대기를 관측했지만, 이 중 무엇이 얼마를 차지하는지 분리한 실험은 하지 않았다.

따라서 이번 채택 범위는 **질문과 기록 준비의 책임 분리, 변경 없는 벡터 재사용, 근거 보존**이다. 현재 파일별 cache 구현을 서비스의 최종 저장 backend로 확정하지 않는다. 후속 최적화는 의미 프롬프트가 아니라 upstream cache의 일괄 영속화·임베딩 batching 또는 적절한 DB backend를 같은 보존 기준에서 비교해야 한다. 이번에 새 DB나 새 LLM 모듈을 추가하지 않았다.

## 의도적으로 남긴 한계

현재 SimpleVectorStore는 새 세대 전체를 저장하고 BM25 corpus 통계도 쓰기 시 재구성한다. 문서별 캐시의 파일 I/O도 필요하다. 따라서 전체 저장 비용이 변경량에만 비례하거나 대규모 서비스가 완성됐다는 주장은 하지 않는다. 원문·기록을 Git으로 공유하고 색인은 private 파생 저장으로 두며, 중앙 서비스로 전환할 경우 저장 backend를 교체할 수 있도록 경계를 분리했다.
