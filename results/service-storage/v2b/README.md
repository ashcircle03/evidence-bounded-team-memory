# 초기 준비 비용 분해와 일괄 캐시 적용

**각자 로컬 실행 + Git 기록 공유를 유지한다.** 원인은 별도 중앙 서버의 부재가 아니라 문서별로 작은 캐시 파일을 확정하던 저장 방식이었다. 기존 LlamaIndex의 multi-key IngestionCache와 배치 임베딩 변환을 재사용했고, 준비/질문 분리와 원문·근거 계약은 유지했다.

Slurm122924는 **COMPLETED / 0:0**, 프로그램 완료·입력·설정·코드·embedding checkpoint 해시를 확인했다. [검증·채택 판정](verification.json), [원결과와 단계 시간](result.json), [고정 기준](PROTOCOL.md), [동결 해시](freeze.json), [자원](accounting.txt), [장부](dispatch.json).

## 무엇이 느렸나

같은229문서(231구절), 같은 GPU·임베딩·tokenizer·검색 설정·Ceph 저장 경로에서 네 조건을 A→B→C→D, D→C→B→A 순서로 측정했다. 매번 빈 색인/캐시를 사용했고 측정 전 임베딩 warmup1회를 별도로 수행했다. 두 번은 원인 진단이며 안정적인 latency 분포 측정은 아니다.

| 조건 | 1회 | 역순 반복 | 중앙값 | 임베딩 batch 호출 | fsync 호출 |
|---|---:|---:|---:|---:|---:|
| A 기존: 문서별 임베딩·파일 저장 |156.71초|139.94초|148.33초|229|475|
| B 임베딩만 배치 |113.01초|83.36초|98.19초|8|475|
| C 캐시만 일괄 저장 |5.51초|4.40초|4.96초|229|19|
| D 캐시·임베딩 둘 다 일괄 처리 |3.81초|9.22초|6.51초|8|19|

기존 A의 전체 시간 합계 중 **fsync가 약89.4%**를 차지했다. 첫 측정에서 구절 분할0.54초, 실제 임베딩2.83초, 캐시 저장 트랜잭션148.54초, 전체 벡터 저장0.52초, BM25 구성0.02초였다. fsync141.00초는 캐시/색인 저장 내부 단계이므로 이 수치들을 모두 더하면 안 된다. 원결과에 inclusive/exclusive 시간을 구분했다.

B의 전체 시간 감소를 전부 배치 효과로 돌릴 수 없다. 같은475번의 fsync 시간도 실행마다 달랐다. **C가 크게 줄어든 결과와 fsync 계측을 함께 볼 때, 반복 영속 쓰기가 주된 병목이라는 판단이 지지된다.** 파일시스템 자체의 어느 내부 과정이 느렸는지까지 분리한 실험은 아니다.

C→D에서 실제 임베딩 계산의 중앙값은 약1.22초→0.20초, batch 호출은229→8이다. D의 전체 시간 중앙값은 C보다 컸으므로 결합형이 언제나 가장 빠르다고 주장하지 않는다. 두 반복에서 파일 저장/동기화 시간이 흔들렸다. 캐시 일괄화가 핵심 개선이고, 배치화는 계산·호출을 줄이는 별도 개선이다.

## 무엇을 바꿨나

- **파일별 IngestionCache → 문서별 키를 담은 한 IngestionCache**: upstream은 이미 여러 키를 저장하고 한 번 persist할 수 있다. 이를 그대로 사용한다.
- **문서마다 IngestionPipeline 실행 → 변경 문서 구절을 모아 한 번 실행**: 실제 embedding batch 크기32는 그대로다. 반환 node ID·순서·벡터 존재를 검사한 뒤 각 문서 키에 연결한다.
- 캐시는 임시 파일에 완성하고 파일 fsync→원자적 교체→디렉터리 fsync로 확정한다. **영속성 보장을 끈 최적화가 아니다.**
- 원문/설정 해시가 같은 문서는 기존 구절·벡터를 읽는다. 초기 캐시가 없을 때 존재하지 않는 문서별 파일을 매번 조회하지 않는다.
- 기존 v1 `documents/<key>.json`과 완성 색인은 삭제하지 않는다. 필요한 기존 키를 새 캐시에 읽어 넣으므로 저장 형식 전환만으로 재임베딩하지 않는다.
- 질문·승인 상태·원문 claim/condition/evidence 구조·모델 프롬프트·다섯 모듈의 공개 계약은 바꾸지 않았다.

레퍼런스: 고정 `llama-index-core0.14.25`의 [IngestionCache와 Pipeline](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/), SimpleKVStore.persist, 기존 VectorStoreIndex/StorageContext. 별도 DB 서버·새 LLM 모듈·중앙 조정자를 추가하지 않았다. [사용·실패 계약](../../../docs/modules/index-lifecycle.md).

## 채택과 남은 비용

사전에 정한 모든 보존 검사와 `D 중앙값 ≤ A 중앙값의50%`를 통과했다(실제 약4.39%). **D를 현재 구현으로 채택한다.** 최적 조건을 탐색해서 고른 최고 점수라는 뜻은 아니다.

일괄 캐시는 전체 읽기/쓰기와 메모리 비용이 있고, 전체 벡터 세대 저장·BM25 재구성도 남아 있다. 변경 없는 문서의 분할/임베딩을 안 한다는 것과 모든 처리 비용이 변경량에 비례한다는 것은 다르다. 첫 질문·재시작은 파일 로드 비용이 남으며 Git pull부터 실제 QA 생성까지의 종단간 속도는 이번 범위가 아니다.

캐시 commit 전 중단은 아직 commit되지 않은 변경 문서 집합을 다시 처리한다. 이미 commit된 변경 없는 문서는 재사용한다. 캐시 commit 후 색인 게시만 실패하면 새 벡터까지 재사용한다. 단위/통합 검사에서 기존 캐시 마이그레이션, 캐시 저장 실패, 색인 게시 실패, 명시적 sync, 승인·재시작을 확인했다. 실제 프로세스 강제 종료 주입은 하지 않았다.

## 검증·비용·재현

- 로컬 전체454개 + 하위87개 검사 통과. 평가 파일명 수정 후 관련16개 재검사 통과.
- source 패키지를 checkout 밖에서 실행한 서비스·인용 검사17개 통과. [로컬 기록](local-checks.json).
- 실행122924: GPU1·CPU8·RAM48G·wall 상한12h, 실제614초. 앞선122923 준비 실패9초도 포함해 총 **623 GPU초 = 10.38 GPU분**. 모델·데이터 복제나 유료 API는 사용하지 않았다.
- 첫 실패는 평가 `profile.py`가 Python 표준 모듈을 가린 이름 충돌이다. instrumentation.py로 바꾸고 `python -m`으로 실행했다. [실패 보존](../v2/README.md).
- [입력](../v1/inputs.json)과 [비교 대상](../v1/retrieval.json)을 같은 파일 바이트로 사용했다. 비교 대상은 검색 실행 후 평가에서만 참조하며 reader 입력에 주지 않았다.
- 실행기: `evaluation/storage_cost/run.py`; 원인 분해: `instrumentation.py`; 변경 전 원본: `indexing_v1.py`. 패킷의 `inputs.json`과 `prior-retrieval.json`은 위 두 파일의 복사본이다. 환경 경로는 [config](config.json), 계산 노드 실행 명령은 [sbatch](run.sbatch)에 있다.
