# 팀 메모리 원문 기반 질의응답 기능명세서

팀 설계 검토안 0.1    |    2026년 11월 22일    |    구현 기준점 PR #2 · a54c8e9

팀원이 남긴 보고와 회의 기록에서 질문에 맞는 사실을 찾고, 누가 어떤 구절을 근거로 답했는지 추적할 수 있게 한다.
이후 정정이 들어오면 검토 전후를 구분하고, 버전이나 조건이 다른 과거 기록도 원래 의미대로 조회할 수 있어야 한다.

### 사용자가 하는 세 가지 일

| 동작 | 사용자가 제공하는 것 | 사용자가 확인할 결과 |
| --- | --- | --- |
| 등록 | 원문과 출처 정보 | 기록 ID, 저장 상태, 비교 결과 또는 후속 작업의 실패 사유 |
| 검토 | 제안 ID와 승인 또는 거절 | 판정된 제안, 효력이 미치는 구절, 새 snapshot |
| 질문 | 자연어 질문. 필요하면 조회 버전 지정 | 답, 주장별 원문 인용, 적용 조건과 관련 검토 상태 |

### 제안하는 구성

Records가 원문과 검토 이력을 소유한다.
Retrieval은 등록 때 비교할 과거 구절을 찾고 질문 때 답변 근거를 고른다.
Relations는 두 기록 사이의 관계를 제안한다.
Answering은 전달받은 근거로 답한다.
Gateway는 세 사용자 동작의 순서와 재시도를 관리한다.

### 현재 기준점과 첫 릴리스 범위

현행 v1.2 어댑터에는 snapshot 조회, 원문 저장, 관계 비교, 검토, 근거 검색, 인용 답변이 있다.
등록 시에는 과거 원문 ID 전체를 비교기에 전달한다.
PR #2의 회귀 테스트는 역할을 미리 넣고 조건 필터를 켠 상태에서 올바른 버전의 역할이 답변 입력까지 도달하는지 확인한다.

첫 릴리스는 단일 workspace의 순차 이력에서 원문 등록부터 승인 후 질의까지 지원한다.
팀 시연과 평가는 같은 진입점에서 실행한다.
다중 브랜치 동시 병합, 신규 UI, 임의의 과거 시각 복원은 후속 범위로 둔다.

## 1 한 질문으로 보는 전체 흐름

아래 A·B·C는 개발자가 같은 조건으로 반복 실행할 인수 사례다.
시스템에는 원문을 차례로 입력한다.
아래의 역할과 관계는 평가자가 대조할 기대값이다.

| 기록 | 입력할 원문 | 구분해야 할 정보 |
| --- | --- | --- |
| A | dataset v1에서는 Petr가 초안을 승인했다. | v1 / 초안 / 승인자 Petr |
| B | dataset v2에서는 Hana가 초안을 승인했다. | v2 / 초안 / 승인자 Hana |
| C | 정정합니다. dataset v1 초안의 승인자는 Mina입니다. | v1 / A의 승인자 정정 / Mina |

### 등록 시점

A와 B를 등록하면 서로 다른 버전의 기록이 남는다.
C가 들어오면 Records가 원문을 저장하고 Retrieval이 비교 대상으로 A의 구절을 찾는다.
Relations가 A와 C의 승인자 구절을 지정해 정정을 제안한다.
Records는 A 원문과 C 원문을 모두 보존하고 제안을 pending으로 기록한다.

### 질문 시점

| 조회 시점과 질문 | 기대 답변의 의미 | 반드시 확인할 근거 |
| --- | --- | --- |
| A·B 등록 후 / v1 초안은 누가 승인했어? | Petr가 승인했다. | A의 v1 조건과 Petr 구절 |
| C 등록 후, 검토 전 / 같은 질문 | 기존 기록은 Petr이며 Mina로 정정하자는 제안이 검토 중이다. | A와 C의 원문, pending 상태 |
| 권한자가 승인한 후 / 같은 질문 | 승인된 정정 기준으로 Mina다. | C의 원문과 승인 상태. 근거 묶음에는 A도 포함 |
| 같은 시점 / v2 초안은 누가 승인했어? | Hana가 승인했다. | B의 v2 조건과 Hana 구절 |

### 답을 추적하는 방법

응답의 claim에서 evidence ID를 따라가면 해당 snapshot 안의 원문 위치나 검토 이벤트에 도달해야 한다.
Mina라는 이름은 C의 원문으로, 정정이 승인됐다는 설명은 검토 상태로 각각 입증한다.
정정 전후에 같은 질문을 보내도 이전 snapshot에서 받은 답의 근거를 다시 열 수 있어야 한다.

## 2 원문 등록과 비교 후보 검색

### F01 원문 저장과 추출 · Records

인증된 등록자가 원문, 소유자, 발화자, 관측 시각, 위치를 제출한다.
Records는 원문 ID와 revision을 발급하고 원문을 그대로 보존한다.
발화자와 소유자는 별개다.
발화자 이름에서 검토 권한을 추정하지 않는다.

주장마다 원문 구절을 붙이고 확인 가능한 조건, 술어와 역할, 시간·근거를 연결한다.
문서 안에 조건이 둘이면 각 조건의 적용 구절을 별도로 지정한다.
모델이 추출한 역할에는 미검증 표시를 유지한다.
원문 위치가 맞지 않는 연결은 제외하고 누락 사유를 남긴다.

**실패와 완료 기준** 추출기가 중단돼도 원문은 조회 가능하며 추출 상태와 진단이 남는다.
같은 요청을 재전송하면 기존 기록 ID를 반환한다.
원문만 있는 구버전 기록도 검색할 수 있어야 한다.

### F02 색인 준비와 과거 구절 선택 · Retrieval

Records가 발급한 snapshot을 받아 추가되거나 바뀐 원문을 색인한다.
이전과 같은 문서·색인 설정은 재사용한다.
새 원문과 같은 workspace의 기존 기록을 대상으로 주제·대상·조건이 겹치는 과거 구절을 선택한다.
새 원문 자체는 후보에서 제외한다.

출력은 비교 기준 snapshot ID, 새 기록 ID, 후보별 과거 기록 ID·구절·순위다.
후보 상한 K와 검색 설정은 실행 기록에 남긴다.
조건이 누락된 과거 기록도 후보가 될 수 있다.
첫 등록은 후보 0건으로 정상 종료한다.

**실패와 완료 기준** 색인 실패 시 저장 영수증과 미완료 단계를 돌려준다.
재시도는 해당 단계부터 진행한다.
검색 실행 실패와 정상 검색 결과 0건을 구분한다.

### F03 관계 제안 · Relations

새 원문 구절과 선택된 과거 구절, 같은 snapshot에서 이미 알려진 관계를 입력받는다.
후보마다 공존·상충·정정·재검토를 판별하고, 근거가 없으면 제안을 생략한다.
제안에는 관계 종류, 양쪽 원문 위치, 이유, 비교 snapshot을 넣는다.
정정은 대체할 양쪽 주장 범위까지 지정한다.

**실패와 완료 기준** 인용 위치가 틀린 제안은 저장 대상에서 제외한다.
일부 비교 실패는 후보별로 반환한다.
모델 시간 초과를 관계 없음으로 취급하면 실패다.
제안 저장 권한은 Records에 둔다.

## 3 검토와 상태의 의미

### F04 제안 저장과 사용자 검토 · Records

Gateway가 Relations의 유효한 제안을 전달하면 Records가 ID를 발급한다.
검토자는 이전 원문의 소유권 및 검토 권한을 확인받은 뒤 제안 ID, 승인·거절, 예상 revision, 재시도 키를 제출한다.
검토 결과와 판정 시각을 새 revision에 저장한다.

| 관계 | 제안 생성 시 | 승인 또는 후속 조회의 효과 |
| --- | --- | --- |
| coexist · 공존 | 조건이 다른 두 구절을 정보성 관계로 기록 | 각 조건별 진술을 독립적으로 인용한다. |
| conflict · 상충 | 동일 조건의 양립하기 어려운 진술을 연결 | 상충이 확인됐음을 표시하고 양쪽을 제시한다. 자동으로 승자를 고르지 않는다. |
| correction · 정정 | 과거와 새 주장의 대상 구절을 함께 지목 | 승인된 경우 지목한 주장 범위에 새 값을 적용한다. 같은 문서의 다른 버전·속성은 유지한다. |
| reconsider · 재검토 | 기존 판단을 재검토할 이유와 구절을 기록 | 승인은 재검토를 허용한다. 새 사실이나 새 결론의 승인을 뜻하지 않는다. |

### 검토 상태가 답에 미치는 영향

pending은 기존 기록과 제안 내용을 구별해 제시한다.
approved는 관계 종류별 효과를 적용한다.
rejected는 기존 값을 유지하며 거절 이력은 남긴다.
review_conflict는 상반된 검토 상태를 표시하고 단일 확정값을 제시하지 않는다.

### 읽기와 동시성

한 번의 질문은 시작 시점의 snapshot ID에 고정한다.
도중에 승인돼도 검색 근거와 답은 같은 버전을 사용한다.
다음 질문부터 새 상태를 읽는다.
원문이 같은 경우 검토 상태만 바뀌어도 재임베딩 없이 새 상태 근거를 결합한다.

**인수 기준** 다른 사용자의 무권한 승인 요청은 상태를 바꾸지 않는다.
서로 다른 두 요청이 같은 예상 revision으로 쓰기를 시도하면 먼저 성공한 쓰기를 보존하고 다른 요청에는 STALE_SNAPSHOT을 돌려준다.

## 4 자연어 질문에서 인용 답변까지

### F05 질문 해석과 근거 구성 · Retrieval

사용자는 질문 문자열만으로 조회할 수 있다.
Gateway가 읽기 권한을 확인하고 snapshot을 고정한다.
Retrieval은 질문에서 대상·버전·시점을 식별하고 어느 질문 구절에서 조건을 읽었는지 기록한다.
사용자가 명시한 필터와 질문 내용이 충돌하면 확인을 요청한다.

검색 구절에서 해당 주장에 적용되는 조건·역할만 선택한다.
선택한 주장이 정정이나 상충과 연결되면 상대편 구절과 검토 상태를 함께 싣는다.
정보가 없는 기록은 조건 미상으로 다룬다.
같은 문단의 다른 주장에 붙은 조건을 가져오지 않는다.

| 근거 상태 | 처리 기준 |
| --- | --- |
| hits | 원문 구절과 출처, 적용 조건, 관련 검토 상태를 고정된 묶음으로 반환한다. |
| no_hits | 검색 성공과 0건을 함께 기록한다. 답변은 근거 부족으로 보류한다. |
| incomplete | 예산 때문에 필수 상대 구절이나 상태가 빠졌으면 누락 이유와 함께 보류한다. |
| 조회 실패 | 색인이 준비되지 않았으면 INDEX_STALE, 검색 실패면 RETRIEVAL_FAILED를 반환한다. 질문 처리 중 색인을 다시 만들지 않는다. |

### F06 답변과 인용 · Answering

입력은 질문과 검증된 근거 묶음이다.
모델에는 선택된 원문·상태 근거만 전달한다.
사실 주장에는 원문 evidence ID를, 검토 상태를 설명하는 주장에는 상태 evidence ID를 연결한다.
검증기는 근거 ID, 원문 위치, snapshot 일치, 필수 상대 구절의 포함을 검사한다.

단일 답은 answered, 버전별 답이 가능하면 conditional, 해소되지 않은 상충은 conflict로 반환한다.
답을 정하려면 질문 조건을 추가해야 할 때는 needs_clarification, 근거가 부족할 때는 abstained와 사유를 반환한다.
인용이 붙지 않은 문장은 별도로 표시하고 확정 주장에 넣지 않는다.

**인수 기준** A·B 사례에서 질문에 v1만 적어도 A를 인용한다.
버전을 생략했고 양쪽 값을 뒷받침할 근거가 충분하면 버전별 답을 준다.
미지원 과거 시각 조회는 TIME_SCOPE_UNAVAILABLE로 응답한다.

## 5 모듈 계약과 오류 처리

아래는 다음 계약에 필요한 최소 정보다.
이름은 패킷 설계를 위한 제안이며 현행 v1.2 요청을 그대로 대체하지 않는다.
공통 봉투에는 계약 버전, request_id, workspace_id, operation을 둔다.
인증된 주체와 권한은 전송 계층이 별도 전달한다.

| 경계와 소유자 | 전달할 필수 정보 | 소비자가 확인할 조건 |
| --- | --- | --- |
| 기록 → 검색·비교<br>Records | source ID, text, owner, speaker, observed_at, location, snapshot ID, 추출 상태, 주장별 구절·조건·역할 | 모든 원문 구절은 source ID와 [start,end), quote로 복원된다. 추출이 없으면 빈 목록과 상태를 준다. |
| 비교 후보 → 관계<br>Retrieval | incoming ID, snapshot ID, 과거 후보별 source ID, 구절, 순위 | 동일 snapshot의 과거 기록만 허용한다. 후보 누락률을 추적할 수 있게 검색 설정을 보존한다. |
| 제안 → 저장<br>Relations | kind, previous, incoming, reason, comparison snapshot ID, 정정의 양쪽 assertion | 제안의 양쪽 인용이 존재해야 한다. reviewer와 효력은 Records가 결정한다. |
| 근거 → 답변<br>Retrieval | query, snapshot ID, coverage, evidence 목록, 미해결 제안 ID, 필수 근거 누락 사유 | 원문 근거는 출처·조건·역할을, 상태 근거는 proposal ID와 snapshot을 가리킨다. |
| 답변 → 사용자<br>Answering | snapshot ID, outcome, claims, 주장별 evidence IDs, 조건, 보류 사유 | 모든 근거 참조는 전달된 묶음 내부에서 해석된다. 주장과 근거를 따로 열어 확인할 수 있다. |

### F07 호출 조정과 복구 · Gateway

등록·검토 쓰기는 idempotency_key와 expected_revision을 요구한다.
동일 주체·작업의 같은 키와 내용은 기존 결과를 재생한다.
같은 키에 다른 내용이면 IDEMPOTENCY_CONFLICT다.
복합 등록은 먼저 완료한 단계와 발급 ID를 기록하고 중단 지점에서 복구한다.

정상 응답은 ok, 일부 성공은 partial과 사용 가능한 data·오류 목록을 반환한다.
잘못된 입력·권한은 invalid, 실행 실패는 error다.
오류에는 code, retryable, 해당 항목 ID를 넣는다.
후속 단계가 실패해도 완료된 원문 저장을 되돌리지 않는다.

offset은 Unicode 코드포인트 기준이며 text[start:end]와 quote가 같아야 한다.
새 계약에서 snapshot 본문 전달을 ID 참조로 바꾸면, 신뢰할 수 있는 Records 조회기로 원문과 상태를 대조한 후 근거를 모델에 전달한다.

## 6 통합 인수 시험과 평가

대표 시험은 팀의 실제 등록·검토·질문 진입점을 사용한다.
원문·자연어 질문·검토 결정만 입력한다.
정답 역할, 검색 필터, 정답 구절을 미리 넣는 시험은 모듈 단위 진단으로 별도 기록한다.

| 시험 | 입력 또는 조작 | 통과 조건 |
| --- | --- | --- |
| T01 버전 분리 | A·B 등록 → v1 질문, v2 질문 | 각각 Petr/A, Hana/B를 답하며 반대 버전의 역할을 섞지 않는다. |
| T02 검토 전후 | C 등록 → 질문 → 승인 → 재질문 | 검토 전에는 기존 값과 제안을 구분한다. 승인 후 Mina와 승인 근거를 제시하고 v2 값은 Hana다. |
| T03 거절·재검토 | 승인 전 snapshot에서 독립 실행 | 정정 거절 시 기존 값 유지. 재검토 승인만으로 이전 결론을 바꾸지 않는다. |
| T04 상충·누락 | 동일 조건에 상충하는 두 원문 등록. 근거 예산도 축소 | 충분한 예산에서는 양쪽 근거, 필수 구절 누락 시 보류와 누락 사유를 반환한다. |
| T05 복구·권한 | 색인 실패 후 동일 등록 재시도. 권한 없는 주체가 승인 | 원문·제안 중복이 없다. 무권한 검토 전후 revision이 같다. |
| T06 이전 기록 | 그래프 없는 기록, 구버전 그래프, 역할이 있는 기록을 함께 조회 | 원문 구절이 복원되고 기존 역할·조건을 보존한다. |
| T07 시간·고립 | 질의 중 승인, 미지원 과거 시각, 다른 workspace에서 같은 ID 요청 | 한 질의의 snapshot이 일정하다. 미지원 시점은 명시적 실패, 타 workspace는 접근 거절이다. |

### 모듈 개선을 판정하는 방법

같은 원문·질문·모델·근거 예산으로 원문 검색 기준 경로와 구조화 Records 경로를 비교한다.
Records는 정답 대비 조건·역할 연결의 정밀도와 재현율, Retrieval은 비교 후보 recall@K와 정답 구절 회수율, Relations는 관계 유형 및 양쪽 구절 정확도를 기록한다.

Answering은 고정 정답 근거로 답·조건·인용을 먼저 평가한다.
전체 시험에서는 세 항목과 outcome을 모두 만족한 문항 수 및 분모를 보고한다.
실패는 최초로 어긋난 단계에 연결한다.
위 7개 시험의 통과는 첫 릴리스 요건이며 일반화 성능은 별도 평가셋에서 판단한다.

## 7 기존 구조 전환과 팀 결정

| 조정 항목 | 전환 방법과 보존할 동작 |
| --- | --- |
| Gateway 축소 | 추출 실행을 Records 내부로, 과거 ID 선정은 Retrieval로 옮긴다. Gateway의 순서 제어·권한 전달·중복 방지·복구 장부는 유지한다. |
| Records 표현 통합 | 구버전 그래프와 역할 데이터를 공통 주장·구절 표현으로 읽는 변환기를 둔다. 기존 저장 파일과 공개 ID를 재작성하지 않고 혼합 버전을 시험한다. |
| 근거 조립 통합 | 조건과 역할을 Retrieval에서 한 번 조립한다. Answering의 중복 재구성은 기존·신규 출력 대조 후 제거하고 공통 참조 검증기는 유지한다. |
| 생성 전략 분리 | 기본 생성·인용 경로를 고정하고 수정·인용 보완 전략을 동일 근거로 비교한다. 개선과 회귀를 확인한 전략만 기본값 변경 대상으로 삼는다. |
| 진입점 통합 | 팀용 ingest / review / ask 경로가 새 조립을 사용하도록 연결한다. 기존 CLI는 호환 기간에 유지하고 명시적 설정으로 이전 경로를 선택할 수 있게 한다. |

### 구현 순서와 인계 조건

**1단계 · 계약 담당과 모듈 담당 공동** A·B·C 원문, 기대 인용, 상태 전이, 오류 예시를 고정한다.
공통 스키마와 호환 변환 규칙을 양쪽 소비자가 검토하면 병렬 구현을 시작한다.

**2단계 · Records와 Retrieval** 원문 보존과 공통 구절 표현을 연결한다.
기존 팀원 검색의 주장 구절 색인·조건 필터 회귀를 유지한다.
전체 비교 대비 후보 누락을 측정한 뒤 후보 상한을 선택한다.

**3단계 · Relations와 Answering** 관계 제안·검토 효과와 고정 근거 답변을 각각 시험한다.
정정 전후 A·C 인용과 v2 독립성을 확인하고 Gateway에 연결한다.

**4단계 · 통합 담당** 같은 진입점에서 T01~T07과 기존 회귀를 실행한다.
실패 시 원문·검토 이력을 보존한 채 이전 읽기 경로로 복귀할 수 있는지 확인한 뒤 기본값을 전환한다.

### 팀 회의에서 정할 사항

계약 버전과 호환 기간, 비교 후보 K와 허용 누락 기준, 모호한 조건에서 재질문하는 기준, 평가셋과 기본 생성 전략을 결정한다.
각 항목의 담당자와 수용 수치는 구현 착수 회의에서 기록한다.
