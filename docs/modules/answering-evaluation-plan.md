# Answering 개발·평가 계획

## 해결할 문제

질문과 고정된 근거 묶음이 주어졌을 때, 질문에 적용되는 주장만 선택하고 각 주장의 조건·검토 상태·출처를 보존한 답을 반환한다. 기본 평가 단위는 (질문에 대한 핵심 답, 적용 조건, 유효 상태, 그 답을 지지하는 허용 근거 집합)이다. 예를 들어 승인된 120ms와 보류 중인 90ms 제안이 있을 때 현재값 질문은 120ms와 그 상태 근거로 답한다. 제안값을 묻는 질문에서는 같은 묶음에서 90ms를 제안으로 표시한다.

공식 진입점은 [answer.generate](answering.md)다. 입력에 포함된 query·snapshot·evidence만 사용한다. 출력은 기존 outcome, claims, conditions, evidence_ids, alternative_group, reason 및 무인용 원문 보존 계약을 따른다. 질문이 모호해서 조건을 명확히 해야 하는 경우와, 질문은 명확하나 근거가 없어 보류하는 경우를 분리한다. 추출·검색·관계 생성·상태 쓰기는 각 소유 모듈에 둔다. historical 입력은 현재 브리지가 명시적으로 거절하므로 첫 평가에서는 미지원으로 따로 집계한다.

## 첫 검증

[현재 어댑터](../../team_memory/adapters/answering.py)는 인용 번호를 문장별 evidence ID로 복원한다. 인용을 가진 claim에는 conditions=[]를 넣고 우선 answered를 반환한다. 미해결 상충 양쪽 source에 서로 다른 인용 문장이 있으면 conflict로 바꾼다. 문장에 드러난 조건이 반환 필드에서 사라지거나, 무관한 상충이 답의 outcome에 영향을 줄 수 있다. 이는 코드에서 확인한 가설이며 실제 오답 수는 측정해야 한다.

1. 기존 조건부 답, 무관한 상충, 미승인 정정의 bundle·고정 생성 출력을 실제 어댑터에 통과시킨다. 생성 직후의 답과 최종 claims·outcome을 대조한다. 입력, 초안, 검사 후 결과, 직렬화 결과 중 처음 틀어진 경계를 기록한다.
2. 생성 답은 맞고 반환 구조에서만 손실되면 그 변환만 고친다. 모델 실험을 추가할 필요가 없다. 기존 계약 검사는 무결성만 확인하므로 의미 정답도 별도로 검사한다.
3. 생성부터 틀리는 유형이 남을 때 같은 Qwen3-8B와 같은 근거 순서·토큰 예산으로 단일 생성 기준선과 현재 공식 어댑터를 비교한다. 두 경로 모두 같은 공개 출력 계약으로 채점한다. 각 방법이 실제로 받은 내용, 모델 원출력과 변환 후 손실, 호출 비용을 보존한다. 이미 존재하는 출력은 입력·프롬프트·모델 설정이 일치할 때만 재사용한다.

## 데이터와 정답

| 목적 | 1차 자료와 평가 단위 |
|---|---|
| 회귀 | 기존 QA 20문항과 상태·인용 8건. 고정 답·허용 근거를 포트의 evidence ID에 매핑하고 중복 scenario를 표시한다. |
| 양쪽 답 보존 | [WikiContradict](https://proceedings.neurips.cc/paper_files/paper/2024/hash/c63819755591ea972f8570beffca6b1b-Abstract-Datasets_and_Benchmarks_Track.html)의 기존 개발 8문항부터 사용한다. 한쪽 문서, 양쪽 문서를 각각 제공해 필요한 답–출처 쌍이 1개에서 2개로 변하는지 본다. 공개 문서에는 팀의 승인 상태를 부여하지 않는다. |
| 자연 회의 응답·보류 | [MeeQA 8문항](../../results/meeqa-pilot/README.md)은 사람이 지정한 허용 구절 집합과 보류 정답을 사용한다. 간접·조건부 답의 적절성, 의미를 잃은 인용, 과잉 보류를 따로 기록한다. 기존 실험은 평가용 호출이라 공식 포트의 성능으로 합산하지 않는다. |
| 팀 상태·조건 | 기존 사례로 채워지지 않는 셀만 합성한다. 같은 묶음에서 질문을 현재값↔제안값으로, 같은 질문에서 검토 이벤트만 보류↔승인으로 바꾼다. 다른 조건의 공존, 무관한 상충, 조건 모호성도 포함한다. 상태와 변경 필드는 이벤트로 정답을 계산한다. 검토 상태의 근거와 실제 값의 근거가 모두 필요한 문항을 표시한다. |
| 다자 기록 일반화 | [EverMemBench-Dynamic](https://huggingface.co/datasets/EverMind-AI/EverMemBench-Dynamic)의 기존 개발 10문항은 2차 확인에 쓴다. 필요한 근거가 묶음에 있는지 먼저 표시하고, 도달하지 않은 근거는 별도 검색 실패로 계산한다. |

개발 자료에서 본 질문은 회귀·진단 전용이다. 후보가 생기면 보지 않은 WikiContradict 문서쌍과 독립 팀 시나리오로 확인한다. 같은 회의·상충 문서쌍·이벤트 계열의 모든 변형은 같은 split에 둔다. 정답에는 허용 outcome, 필수 주장, 대체 가능한 근거 집합, 금지 상태·금지 주장을 기록한다. 충분·부분·없음 및 단일·다중 근거의 분포를 표로 고정하고 의미가 애매한 정답은 구현 전에 검토한다.

## 레퍼런스에서 사용할 기능

| 실제 구현 | 입력과 출력, 적용 조건 |
|---|---|
| 기존 LlamaIndex 기반 generate_evidence | 고정 bundle의 ID·원문·상태를 번호가 붙은 근거로 직렬화하고 한 번 생성한다. ID와 원문 위치 간 대응을 끝까지 유지한다. |
| [Adaptive QA few-shot](https://github.com/Shaier/Adaptive_QA/blob/f72bdb3e5d1f4bf83a3dd84596039b67ddd145e8/experiments/few_shot.py) | 대안 누락이 확인될 때만 후보로 사용한다. 원래의 답과 출처를 함께 내는 예시 구조를 보존하고, 대안마다 조건과 evidence ID를 연결한다. 새 문서 ID가 추가됐다는 사실만으로 수정 답을 채택하지 않는다. |
| [ALCE citation evaluation](https://github.com/princeton-nlp/ALCE/blob/main/eval.py) | 결과 평가에서 한 주장에 인용된 근거를 합쳐 의미 지지를 검사하고, 다중 인용은 불필요한 출처도 확인한다. 팀 상태는 별도의 결정론적 정답과 대조한다. 자동 NLI와 고정 정답이 갈리면 원문으로 판정한다. |
| [ConflictScore 원형과 기존 연결 감사](../reference-composition-audit.md) | 반박 판단이 필요한 실패가 확인된 경우에만 비교한다. 답 전체가 아닌 개별 주장과 각 근거를 입력하되 조건·시점·귀속이 분해 중 사라지면 후보를 기각한다. |

추가 기법은 먼저 원형의 단위와 본 프로젝트의 evidence ID가 대응하는 작은 예제로 확인한다. 한 번에 한 원인만 바꾸고 기준선이 충분하면 거기서 종료한다.

## 채택 판단

주 지표는 필수 답·조건·상태·허용 근거를 모두 만족하고 금지 주장이 없는 문항 수다. 보조 지표는 필수 답–근거 쌍 재현율, 출력 주장 중 인용이 의미상 지지하는 비율, 상충 양쪽 보존, 상태 위반, 답 가능 문항의 잘못된 보류, 답 불가 문항의 올바른 보류다. 원문 위치 일치와 의미 지지는 별도로 보고한다. 확인 질문도 기대 outcome으로 채점한다. 다중 출처가 필요한 경우 하나의 정답 집합 안에서 모두 충족해야 한다.

채택은 사전 합의한 목표 오류의 독립 보류 사례 개선, 기존에 맞힌 QA와 상태·인용 회귀 0건, 새 미승인값 승격·근거 없는 주장 0건을 요구한다. 모든 수치는 분모와 사례별 개선/퇴행을 함께 낸다. 동일 성과면 호출·토큰·지연이 작은 경로를 선택한다. 최종 후보만 실제 retrieval bundle으로 다시 확인하며, 검색 손실과 answering 손실을 분리한다. 새 모델, 학습, 대규모 실행은 첫 단계 범위 밖이다.
